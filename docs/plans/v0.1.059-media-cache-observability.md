# v0.1.59 実装計画書: メディアキャッシュ可観測性向上（`snapshot --status` キャッシュ集計 & `doctor` `[MEDIA_CACHE_AVAILABLE]` 案内）

- **対象バージョン**: `v0.1.59`（`README.md` の最新化コミット `f3e5a41`, `99cee97` を含む）
- **作成日**: 2026-11-24
- **ステータス**: **Implemented（v0.1.59）**
- **前提**: `v0.1.56`（`media/_cache/` オプトインキャッシュ & `--from-snapshot` 展開）、`v0.1.58`（`js-yaml@^4.1.0` 依存追加）完了済み。Schema は **v8** のまま変更なし。

---

## 1. 背景と目的

`v0.1.56` で導入した `media/_cache/` によりオフライン記事・画像復元が可能になった一方、現在の運用画面では以下の 2 点の可観測性ギャップが残っている：

1. **`emit snapshot --status` / `sync_snapshot({ action: "status" })`**: 記事数・メディアメタデータ数は表示されるが、`media/_cache/` に現在何件・何 MiB のバイナリがキャッシュされているか（上限 `200` 件 / `512 MiB` に対する使用状況）が確認できない。
2. **`emit doctor` / `sync_doctor`**: ローカル記事が参照するメディアが `media/` に未展開の場合、すでに `media/_cache/` にキャッシュ済みであっても一律オンラインの `emit pull-media --article <id>` だけを案内しており、0-HTTP で展開できる手段（`emit pull --from-snapshot`）に気付けない。

本計画では上記 2 点を 0-HTTP のまま補完し、`README.md` の最新化と合わせて `v0.1.59` としてリリースする。

---

## 2. 設計方針

### 2.1 候補 1: `emit doctor` での `[MEDIA_CACHE_AVAILABLE]` 案内 (`src/sync/doctor.ts`)

- **対象抽出**: `missingMedia` を構築する `detailed.normalRefs` ループ（`src/sync/doctor.ts:846-855`）で、既存の `probeKey(ref)` 相当のストレージキー抽出を行う（`checkMediaUrls` オプションの有無に関係なくキー抽出のみローカル実行）。
- **キャッシュ照合（0-HTTP）**:
  - 抽出した `storageKey` に対して `options.cache.getSnapshotMediaByStorageKey(storageKey)` を参照。
  - `cachedAt != null && cachePath != null` かつ `fs.existsSync(path.join(options.workspaceRoot, cachePath))` が真であれば `cacheAvailableKeys: Set<string>` に記録する。
- **チェック結果の出力**:
  - 既存の `media_references` warning（`media/` 実体基準、`status: 'warning'`）の挙動やメッセージ仕様は壊さず維持する。
  - `cacheAvailableKeys.size > 0` の場合、追加の info check（`id: 'media_cache_available'`, `name: 'Offline Media Cache'`, `status: 'ok'`）を `checks` に追加する：
    - `message`: `[MEDIA_CACHE_AVAILABLE] ${cacheAvailableKeys.size} missing media reference(s) are already cached in media/_cache/ — run "emit pull --from-snapshot" to materialize them offline (0 HTTP requests).`
    - `details`: 該当 `storageKey` 一覧（配列）。
  - また、`missingMedia.length > 0 && cacheAvailableKeys.size > 0` の場合、`media_references` の `suggestion` が未設定であれば `Run "emit pull --from-snapshot" to materialize cached media from media/_cache/ without network requests.` を添える（`checkMediaUrls` 時は既存詳細 suggestion を維持）。
- **キー抽出の注意（corrupt 検知との整合）**: 照合対象キーは `probeKey(ref)` と同一条件（`VALID_MEDIA_FILE_KEY` 通過済みの `<ulid>.<ext>` のみ、slash-bearing migrated keys は除外 — v0.1.56 の declared non-scope と一致）で抽出する。さらに `media_stage.ts:812-819` と同じ size 突合（`snapRow.size >= 0 && stat.size !== snapRow.size` → `[MEDIA_CACHE_CORRUPT]` 相当として cacheAvailableKeys に含めない、details に corrupt キーを併記）を行う。これにより doctor が案内した `--from-snapshot` が実際に 0-HTTP で成功することが保証される。
- **後方互換性**: `status: 'ok'` の情報チェックのため `overallStatus`（`healthy` / `warnings` / `errors`）や既存テストへの破壊的影響はない。

### 2.2 候補 2: `emit snapshot --status` / `sync_snapshot(status)` でのキャッシュ件数・容量表示

- **Layer 2 (`src/sync/snapshot/types.ts`, `src/sync/snapshot/index.ts`)**:
  - `SnapshotMediaCacheStatus` 型を追加：
    ```ts
    export interface SnapshotMediaCacheStatus {
      cachedCount: number;
      totalBytes: number;
    }
    ```
  - `SnapshotStatusResult` に `mediaCache?: SnapshotMediaCacheStatus`（オプショナル）を追加し、第 3 引数 `workspaceRoot` 未指定時はフィールド自体を省略する（既存呼び出し側・MCP JSON の後方互換を最大化）。
  - `getWorkspaceSnapshotStatus(cache: CacheDatabase, collection = 'posts', workspaceRoot?: string)` にオプショナルな第 3 引数 `workspaceRoot` を追加（既存の 2 引数呼び出しを壊さない）。
  - `cache.listCachedSnapshotMedia()` を走査し、`row.cachePath` の実ファイル存在を `fs.statSync` で確認（`stat.size` を加算）し、`cachedCount` と `totalBytes` を集計する。スナップショット自体が存在しない場合（`meta === null`）も `_cache/` に孤児ファイルが残っているケースがあるため、集計は `meta` の有無に依存せず常時行う。
- **Presentation (`src/presentation/media_report.ts`)**:
  - `formatMediaCacheStatusLine(mediaCache: { cachedCount: number; totalBytes: number }): string | null` を追加（`cachedCount === 0` なら `null`、1 件以上なら `Media cache: ${cachedCount} file(s) (${(totalBytes / (1024 * 1024)).toFixed(2)} MiB in media/_cache/)` を整形）。CLI 側から利用。
- **CLI (`src/cli/commands/snapshot.ts`) & MCP (`src/mcp/tools/sync-snapshot.ts`)**:
  - CLI (`--status`): `getWorkspaceSnapshotStatus(ctx.cache, collection, ctx.root)` を呼び、**`meta === null`（スナップショット無し）の早 return 経路でも** `formatMediaCacheStatusLine(status.mediaCache)` が非 `null` なら孤児キャッシュ案内として併記する。
  - MCP (`action === 'status'`): `getWorkspaceSnapshotStatus(ctx.cache, collection, ctx.root)` を呼び、返却 JSON に `mediaCache: status.mediaCache` を含める。

## 3. アーキテクチャ・レイヤリング確認

- **Schema 変更なし**: `cache.db` は Schema v8 のまま変更しない。
- **Layering / Sibling 境界**:
  - `src/sync/doctor.ts` は既に `src/db/cache.ts` と `node:fs` / `node:path` を使用しており新規エッジ不要。
  - `src/sync/snapshot/index.ts` も既に `cache.listCachedSnapshotMedia()` と `node:fs` を使用しており新規エッジ不要。
  - `src/cli/commands/snapshot.ts` / `src/mcp/tools/sync-snapshot.ts` は `ALLOWED_LAYER_2_SYMBOLS.snapshot` の既存許可シンボル `getWorkspaceSnapshotStatus` をそのまま利用する。
  - **重要**: `formatMediaCacheStatusLine()` の引数型に新規エクスポート型 `SnapshotMediaCacheStatus` を使うと、Layer 3（`src/presentation/`）からの import が `ALLOWED_LAYER_2_SYMBOLS.snapshot` に未登録のため layering テストで失敗する。回避策として **`media_report.ts` の引数を構造的型 `{ cachedCount: number; totalBytes: number }`** とし、新規シンボルの allowlist 追加を不要にする（v0.1.56 で `SnapshotPruneCacheResult` を追加した際のような明示承認・テスト更新も不要）。
