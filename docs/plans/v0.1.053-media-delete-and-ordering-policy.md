## 1. 背景と設計原則（メディアライフサイクルの対称性完成）

現行（`v0.1.52`）の Emit はメディアの全ライフサイクルを扱うが、**リモート本体系の削除入口だけが欠落**している：

| ライフサイクル | 現状の実装 | 缺口 |
| --- | --- | --- |
| 登録（アップロード） | `emit push-media` Mode B（`src/sync/media/push_media.ts`）＋記事 push の `media/drafts/*` 自動昇格 | — |
| メタ更新 | `emit push-media` Mode A/C → `updateRemoteMediaMetadata()`（`src/client/media.ts`） | — |
| 一覧・検索 | `emit pull-media` / `emit media-search` / `sync_media_search` | — |
| **削除** | **CLI / MCP に入口なし**。`compensateOrphanMedia()`（`src/client/media.ts:360`）が内部補償として `DELETE /_emdash/api/media/{mediaId}` を叩くのみ。`deleteMediaState*()`（`src/db/cache.ts:677,682`）は **キャッシュ行**の削除でありリモート物理削除ではない | **本要望** |

一方、必要な安全部品はすべて既存実装として存在する：

1. **参照保護**: `collectPruneProtectionSets(workspaceRoot, collection)`（`src/sync/media/prune_protect.ts:61`）が workspace 全記事（`draft/`, `published/`, `conflicts/` を含め、`.deleted.md` は除外）から本文 storageKey と `featuredImage` / 本文 ULID の mediaId を両 ID 空間で収集済み。
2. **削除エンドポイント**: `mediaDetailEndpoint(origin, mediaId)`（`src/client/endpoints.ts:61`）に対する `DELETE` は Phase 0 spike で実機検証済み（HTTP 200 → GET 404、`docs/plans/v0.1.029-local-first-media-pipeline-design.md` L425）。
3. **安全思想の雛形**: 記事削除 `emit delete`（`src/sync/delete.ts`）の `dryRun` / 明示確認フラグ / 保護エラークラス（G13 `CanonicalHasUnpushedEditsError`・G14 `QuarantinedPathRequiredError` のような**番号付きガードとして `GUARD_REGISTRY` に登録された専用クラス**の系譜）/ `.deleted.md` 救出バックアップ。
4. **ローカル整合性**: `cache.deleteMediaState(storageKey)`（Axis 6 の呼び出し禁止対象外、media 系での使用実績あり）と companion YAML 規則（所有権は `id:` フィールドのみ、ファイル名 ULID を解釈しない）。

## 2. 詳細設計仕様

### 2.1 `<target>` 解決（`push-media` と同一の分類規則・Two Media ID Spaces 厳守）

`deleteMedia(options: DeleteMediaOptions): Promise<DeleteMediaResult>` は 1 件以上の `targets: string[]` を受け取り、各 `target` を `pushMedia()` と**同一の優先順序**で分類する（ユーザーの心智モデルを統一するため、分類規則は `push_media.ts` の既存ヘルパ `expandHomePath()` / `isExplicitLocalPathTarget()` を `src/sync/media/target_resolve.ts`（新規・Layer 2）へ抽出して共有する。`push_media.ts` 側の挙動は完全不変）。

| 優先順 | `<target>` の種別 | 判定条件 | D1 `mediaId` の解決経路 |
| --- | --- | --- | --- |
| **T-A: ローカル companion YAML** | `media/<stem>.yaml` | 実在し `.yaml` で終わる（`legacy_*.yaml` は拒否） | `.yaml` の `id:` → `toMediaRecordId()` 検証。所有権は companion のみ（Invariant 3: ファイル名から ULID を解釈しない） |
| **T-B: ローカルミラー画像** | `media/<stem>.<ext>` | `media/` 直下の通常ファイル | `mediaRecordIdForStem(mediaDir, stem)` → companion `id:`。companion 無しは `MEDIA_COMPANION_NOT_FOUND`（所有権を決定できない資産には一切触れない — pruning と同一規則） |
| **T-C: `<mediaId>` / `<storageKey>`** | 26 文字 ULID または R2 key | 実在せず、明示ファイルパス接頭辞（`./`, `../`, `/`, `~/`, `media/`, `.yaml` 末尾）を持たない | ① `toMediaRecordId()` 非 null → 確定。② `toStorageKey()` 非 null → `cache.getMediaState(storageKey)` → companion YAML（`collectLocalMirrorIndex()`）→ 最終手段として `collectRemoteStorageKeys()` のリモート一覧 walk で `recordsByStorageKey` から D1 `id` を逆引き |

- **DELETE は `mediaId`（D1 レコード ID）専用**。`storageKey` をそのままエンドポイントへ渡さない（Two Media ID Spaces 不変条件。branded types `MediaRecordId` / `StorageKey` が型レベルで強制）。
- タイポされたファイルパスは Mode C にフォールスルーせず即 `MISSING_LOCAL_IMAGE_FILE`（`push-media` の既存規則と同一）。

### 2.2 安全ガード G20 `MEDIA_IN_USE_PROTECTION`（参照中メディアのデフォルト拒否）

削除実行前に `collectPruneProtectionSets()` を 1 回 evaluate し、解決済み各ターゲットについて:

- storageKey の `storageKeyToMarkdownRef()` stem または extension-stripped key が `protectedStems` に一致、または
- mediaId（uppercase）が `protectedRecordIds` に一致

した場合、**デフォルトで拒否**する。**参照元記事パス一覧（`referencedBy`）を返す必要がある**ため、`PruneProtectionSets` を拡張する（指摘 5 対応・実測: 現行 `src/sync/media/prune_protect.ts:29-39` は 2 つの Set のみ返し参照元パスを保持しない）:

```ts
// src/sync/media/prune_protect.ts（拡張）
export interface PruneProtectionSets {
  protectedStems: Set<string>;
  protectedRecordIds: Set<string>;
  /** Rev.2 追加: stem / recordId → その参照を含む記事の workspace 相対パス一覧（昇順・重複排除）。
   *  prune 側は既存 2 Set のみを参照し続けるため、prune 挙動は完全不変。 */
  referencingFilesByStem: Map<string, string[]>;
  referencingFilesByRecordId: Map<string, string[]>;
}
```

保護エラーは **G13（`CANONICAL_HAS_UNPUSHED_EDITS` / `CanonicalHasUnpushedEditsError`）・G14（`QUARANTINED_PATH_REQUIRED` / `QuarantinedPathRequiredError`）と同一のパターン**で、番号付きガード専用クラスとして実装する:

```ts
// src/sync/media/delete_media.ts（新規）
export class MediaInUseDeletionForbiddenError extends Error {
  public readonly code = 'MEDIA_IN_USE_PROTECTION'; // GUARD_REGISTRY G20 の codes と一致させる
  // details: mediaId, storageKey, referencedBy: string[]（参照記事の相対パス一覧）
}
```

- **ガード体系の登録規則（指摘 2 対応・二重登録禁止）**: `src/sync/guards.ts:103-111` の `PROTECTION_ERROR_CODES` は「**`GUARD_REGISTRY` の外に存在する**保護エラー」の集合である。したがって `MEDIA_IN_USE_PROTECTION` は **`GUARD_REGISTRY` の G20 のみに登録**し、`PROTECTION_ERROR_CODES` には**追加しない**（両方に入れると `tests/guards.test.ts` Rule 3 の重複排他検査に反する）。クラス名も体系に合わせて `MediaInUseDeletionForbiddenError` とする。
- **`GUARD_REGISTRY` への G20 登録**（`id: 20`, `name: 'MEDIA_IN_USE_PROTECTION'`, `codes: ['MEDIA_IN_USE_PROTECTION']`, `severity: 'error'`）。あわせて `GuardStage` 型（`src/sync/guards.ts:34`）に **`'media-delete'` stage を追加**する。
- **`tests/guards.test.ts` のアサーション追随**: Rule 3 の連番を `1..19` → `Array.from({ length: 20 }, ...)` へ。Rule 5 は active guard（`codes.length > 0`）が 16 → **17**、code 総数が 20 → **21**（新規 code `MEDIA_IN_USE_PROTECTION` 1 件増）となり、新規 code のテストアサーション必須要件を `tests/delete_media.test.ts` が充足する。
- **Bypass は存在しない**（v0.1.53 では `--force` を意図的に実装しない）。参照中の資産を消す唯一の正しい手順は「先に記事を直して push し、再実行する」ことである。要望書が提案した `--force` より厳格な安全側設計（G19 と同じ「破壊の自覚を要求するのではなく、破壊そのものを入口にしない」系譜）。
- **Epistemic 限界の明示**（Invariant 6 と同源）: 参照スキャンは **workspace に存在する記事のみ**が対象。30+30 同期窓の外・未 pull のリモート記事からの参照は検知できない。dry-run / 実行結果には必ず次を追加する:
  `[LOCAL_REFERENCE_SCAN_ONLY] references from articles outside this workspace are NOT checked`

### 2.3 削除パイプライン（対象ごと、逐次）

**Rev.2 順序確定（指摘 3・4 対応）**: ローカル完結処理（G20 チェック・dry-run 返却）をネットワーク通信より前に置き、破壊的ローカル操作（バックアップ退避・unlink）はリモート DELETE 成功後にのみ実行する。

```text
[0] target 解決（§2.1）→ { mediaId: MediaRecordId, storageKey?, mirrorPaths? }
      └ 解決不能 → per-item error（解決段階は ApiError で MEDIA_COMPANION_NOT_FOUND / MISSING_LOCAL_IMAGE_FILE）
[1] G20 ローカル参照チェック（§2.2 — workspace 読取のみ、ネットワーク 0 回）
      └ 参照中 → items[] に action: 'refused' + referencedBy を収集し次のターゲットへ（throw しない。§2.6 参照）
[2] dry-run ならここで結果返却（GET / DELETE 含むネットワーク通信 0 回、認証トークン不要）
[3] GET /_emdash/api/media/{mediaId}（fetchRemoteMediaDetail 相当）で実在確認
      ├ 404            → action: 'already-deleted'（リモート削除済み。[5] のローカル整理のみ実行、per-item warning）
      ├ status pending/failed → per-item error MEDIA_DELETE_PRECONDITION_FAILED（pending は compensateOrphanMedia の領域。ユーザー削除の口にはしない）
      └ ready          → 続行
[4] DELETE /_emdash/api/media/{mediaId}（createAuthedFetch）
      ├ 2xx / 404 → 続行（404 は [3] の race で「既に消えた」＝成功として扱う。compensateOrphanMedia と同一語義）
      └ その他    → per-item error REMOTE_MEDIA_DELETE_FAILED（新規 code、OPERATIONAL_ERROR_CODES へ追加）。
                    ローカルは一切変更しない（リモート失敗＝ローカル不変の原子性）
[5] DELETE 成功後のみローカル整理:
      a. 救出バックアップ退避（--no-backup でスキップ）: companion YAML を media/_trash/<stem>.deleted.yaml へ、
         ミラーバイナリを media/_trash/<stem>.deleted.<ext> へ move（コピーではなく移動。記事削除の
         「remote DELETE 確認後に rescue copy 書く」delete.ts:296-305 と同一順序）。
      b. cache.deleteMediaState(storageKey) ＋ 残った media/<stem>.<ext> / .yaml の unlink
      （companion に storageKey が無い場合は storageKeyFromMediaMeta() で url から復元してから削除）
```

- **バックアップ命名（Rev.2 統一・指摘 1 対応）**: Markdown ではないため `.deleted.md` サフィックスは使わない。companion YAML は `media/_trash/<stem>.deleted.yaml`、バイナリは `media/_trash/<stem>.deleted.<ext>` に統一する。
- **順序保証と原子性**: 1 レコード完結ごとに [4]→[5] を実行する。途中で失敗したアイテムは per-item error として収集し、他のアイテムの処理は継続する（`push-media` の items 配列モデルと同一）。リモート DELETE 失敗時にローカル側で先に書いたものは何もない（バックアップは成功後の move のみ）。全体 exit code は §2.6 の定式化に従う。
- **R2 オブジェクト実削除の検証**: サーバーが D1 レコード削除に加えて R2 オブジェクトも物理削除するかは Emit の保証範囲外。削除後の GET 404 を確認して成功とみなし、ファイルルート（`/_emdash/api/media/file/<storageKey>`）の挙動には言及しない（epistemic rule: 観測できない事実を主張しない）。
- **`emit doctor` との整合（Rev.2 追加・指摘 1 対応）**: 実測 `src/sync/doctor.ts:683-686` は `media/` 直下 readdir で `isFile()` 判定を持たず、`f !== 'drafts'` の全エントリを `nonYamlMediaFiles` に積む。そのため `media/_trash/` ディレクトリはそのままでは `:1022-1028` の `unattributableFiles` に `media/_trash` として拾われ誤 Warning を出す。**`src/sync/doctor.ts` を変更対象に含め**、`:684` の除外条件を `f !== 'drafts' && f !== '_trash'` に拡張する（`isFile()` 化は既存ミラー命名検査への影響範囲が大きいため行わない）。`tests/doctor.test.ts` に「`media/_trash/` を作っても unattributable warning が出ない」ケースを追加する。

### 2.5 CLI / MCP インターフェース仕様

#### 1. CLI: `emit delete-media`（`src/cli/commands/media.ts` に `registerDeleteMediaCommand`、`src/bin/emit.ts` で登録）

```bash
emit delete-media <targets...> [--dry-run] [--no-backup] [-p, --profile <name>]
```

- 例 1: `emit delete-media media/01KEY.01KEY2.jpg`（ローカルミラー画像 → companion `id:` から解決）
- 例 2: `emit delete-media 01M6...T0J0 --dry-run`（mediaId 指定の事前確認）
- **`--yes` / 対話確認は設けない**: 「明示フラグを渡せば消える」より「参照チェックを通らなければ消えない」ほうが Emit のガード系譜に一貫する。確認機構は `--dry-run` を推奨文言で促す形とする（記事削除の `--allow-delete-published` は「published 実データ」という追加条件に対する gate であり、メディアには該当概念がない）。
- 出力（presentation 関数 `formatMediaDeleteReport()` を `src/presentation/media_report.ts` に追加し CLI/MCP 共有）:

```text
🗑️  Media Deletion (2 targets) — DRY RUN
   ✔ would delete: media/01KEY.01KEY2.jpg → mediaId 01M6...（storageKey 01KEY.01KEY2.jpg, 1.2 MiB）
     refs: none（local workspace scan only）
   ⛔ refused [MEDIA_IN_USE_PROTECTION]: media/01AB.jpg → referenced by posts/published/20261108_...-trip.md
   [LOCAL_REFERENCE_SCAN_ONLY] references from articles outside this workspace are NOT checked
```

- エラー時は Axis 8 に従い `reportActionFailure(err)`。dry-run は認証トークン不要（CLI は既存の `resolveContext(profile, { optionalAuth: isDryRun })` を踏襲 — `src/cli/commands/delete.ts:45` の前例どおり）。
- **MCP 側の無トークン dry-run（Rev.2 明記・指摘 3 対応）**: MCP の context resolver は現在常にトークン解決を要求する（実測 `src/mcp/server.ts:140-144`: `resolveAuth()` が null なら即 Error）。v0.1.53 では **resolver を変更せず**、`sync_delete_media` の無トークン dry-run は非対応とし、ツール description・`docs/cli-and-mcp-reference.md` に「dry-run with zero token is CLI-only; MCP requires an authenticated profile」と明記する（オフライン診断の入口は `emit delete-media --dry-run` と `emit doctor` / `sync_media_search(offline: true)` で足りており、resolver の auth 契約変更は Ask First 級の変更を伴うため本リリースの範囲外）。

#### 2. MCP: `sync_delete_media`（`src/mcp/tools/sync-delete-media.ts` 新規、`src/mcp/server.ts` で登録）

- **Zod スキーマ**:
  - `targets: z.array(z.string()).min(1).describe('One or more local mirror paths ("media/<stem>.<ext>" / "media/<stem>.yaml"), storageKeys, or 26-char mediaIds.')`
  - `dryRun: z.boolean().optional()`
  - `noBackup: z.boolean().optional()`
  - `profile: z.string().optional()`
- 戻り値: items 配列 `{ target, action: 'deleted' | 'already-deleted' | 'refused', mediaId?, storageKey?, referencedBy?: string[], error?: { code, message } }` ＋ `[LOCAL_REFERENCE_SCAN_ONLY]` warning ＋ `_meta`（Axis 9 `withResolvedContext()` 準拠）。
- Axis 9: `formatToolError()` で全例外をラップ。`MediaInUseDeletionForbiddenError` は保護系として `tool-errors.ts` の既存保護クラス分岐（G13/G14 クラスの扱いと同型）に追加。dry-run preview は正常返却、実行時の拒否は §2.6 の定式化どおり throw → `formatToolError` 経路。

### 2.6 結果収集と最終 throw の定式化（Rev.2 追加・指摘 6 対応）

`deleteMedia()` は**ターゲットループ内で決して throw しない**。全ターゲットの結果を `items: DeleteMediaItemResult[]` に収集する（`action: 'deleted' | 'already-deleted' | 'refused'` ＋ per-item `error?: { code, message }`）。

- **dry-run**: レポートを組み立てて**正常返却**（preview。G20 拒否も `refused` item として一覧に載るだけ）。
- **実行モードで全 items が成功（deleted / already-deleted）**: 正常返却。
- **実行モードで 1 件でも `refused`（G20）がある**: レポート（items 一覧・`referencedBy`・`[LOCAL_REFERENCE_SCAN_ONLY]`）を presentation で組み立てた**後で**、`MediaInUseDeletionForbiddenError` を throw（Axis 8 `reportActionFailure` / Axis 9 `formatToolError` が統一出力へ変換。エラー自体が拒否 items の集約サマリと referencedBy を保持する）。
- **実行モードで `refused` は無いが per-item error がある**: 同様にレポート後に最後の失敗を `ApiError`（`REMOTE_MEDIA_DELETE_FAILED` / `MEDIA_DELETE_PRECONDITION_FAILED`）として throw。
- この定式化により「バッチ継続して全ターゲットの判定を一覧表示」と「Axis 8/9 の単一エラー出口」が両立する（部分成功時は exit code 1、throw 前に完了済みアイテムの実行結果はレポートで必ず開示する）。

## 4. メディア順序ポリシーの明文化（要望2 の Emit 側最終回答）

**不変条件として AGENTS.md §2（Invariant 3 のメディア項目に統合）へ追加**:

> **Media ordering is server-authoritative.** Emit never parses image metadata (EXIF), never sorts uploads to influence `createdAt`, and never attempts to rewrite or re-sort remote media records. List order derives from EmDash's ULID-keyed record ids (`ORDER BY id DESC` = newest-first). If ordering control is ever required, it belongs to the EmDash API (server-side sort key), not to Emit.

反映先:

1. `AGENTS.md` §2（上記宣言）＋ Rule ⇔ Enforcer Table へ行追加（Enforcement Level: 宣言された非範囲（declared non-scope）。強制は「Phase A payload に順序系フィールドが無い」を `tests/media_upload.test.ts` で固定し、EXIF 系 import を禁止する新規 Axis は設けない — Ask First カテゴリ 1 がゲートとして機能するため十分）。
2. `docs/media-pipeline.md` §3.3 に 1 行: 「`createdAt` はサーバーが ULID 発行時に確定する（＝送信順）。Emit は EXIF を読まず、並び替えオプションを持たない」。
3. `emit push-media` のコマンド help・リファレンスに同じ趣旨の注記。

**却下した選択肢と理由（決定記録）**:

| 要望 | 判定 | 理由 |
| --- | --- | --- |
| `--order-by exif` | **却下** | EXIF パーサ = 実行時依存の追加は「zero native dependencies / 依存最小化」方針への最初の逸脱。サーバーデータ（createdAt）をクライアントで修理しない原則と同源。dedup（`sha1:<hex>` + `deduplicate: true`）により同一バイト再送では新 createdAt も得られないため、クライアント側並び替えは順序保証として原理的に不完全 |
| createdAt / sort key 後付け更新 | **EmDash サーバー側要望へ転送** | `PUT /_emdash/api/media/{id}` の更新可能フィールドは alt/caption 系のみ（実測済み）。ULID 由来的 id の書換えは ID 空間設計と衝突。Emit 側に実装余地なし |
