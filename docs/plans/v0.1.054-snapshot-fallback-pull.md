## 1. 背景と目的

`emit snapshot capture`（v0.1.47 導入、Schema v6）は全ライブラリのメタデータ＋**変換済み本文 Markdown** を `.emit/cache.db` に保存するが、これを消費するのは現状 `article-search` / `media-search` のオフライン検索のみ。通信環境が無い状況で `pull` は完全に失敗する。

**目的**: 明示オプションによる **Snapshot ベースの劣化フォールバック Pull** を追加し、オフラインでも記事 Markdown（frontmatter + 本文）をワークスペースに復元・編集・`emit diff` 確認できるようにする。完全な Pull の代替ではなく、**「次回オンライン Pull がローカル編集を保持したまま正規ベースラインへシームレスに昇格できる、暫定的なローカル復元」**として設計する。

## 2. 設計原則（3 つの不可侵ルール）

1. **明示オプションのみ・自動フォールバックなし**: `emit pull --from-snapshot` / `sync_pull(fromSnapshot: true)`。通信失敗時の暗黙切り替えはしない（鮮度事故防止）。`snapshot_meta` が無い collection での使用は即エラー（`SNAPSHOT_NOT_AVAILABLE`）。
2. **Track 1 rev を絶対に捏造しない**（Two-Track Revision 不変条件の延長）:
   - snapshot pull は `commitArticleSnapshot()` を通じて `base_snapshots` と `sync_state` をアトミックに保存する（**Axis 6 遵守**）が、`base_snapshots.rev`（Track 1）には偽のサーバー数値トークンではなく **明示的なセンチネル `'snapshot:' + comparisonRev`** を格納する。
   - Push 時は `src/sync/push/guards.ts`（`evaluatePrePreflightGuards`）が `baseSnapshot?.rev.startsWith('snapshot:')` を検知して **`PULL_REQUIRED_BEFORE_PUSH` で確実にブロック**するため、センチネル文字列が `PUT { _rev }` に流出することは絶対にない。
   - `sync_state.remote_rev` には snapshot の Track 2 `comparison_rev` をそのまま保存し、次回オンライン Pull が「snapshot 時点 rev vs 最新 rev」で正しく差分検出しつつ `base_snapshots.rev` を実サーバーの Track 1 `remoteRev` へ昇格させる。
3. **Epistemic 宣言**: 結果に必ず `[SNAPSHOT_FALLBACK captured_at=<ISO>]` warning を付与。snapshot に ULID が無い場合は「不在」ではなく `SNAPSHOT_MISS`（通信なしでは確認不能）として報告する（`[WALK_INCOMPLETE]` と同思想）。

## 3. Schema v7: `snapshot_articles` のフィールド拡張（Ask First・カテゴリ2）

`CURRENT_CACHE_SCHEMA_VERSION: 6 → 7`。既存の「`PRAGMA table_info` + 条件付き `ALTER TABLE`」パターン（Migration 1/2/4 と同型、`migrations.ts:262-305,329-335`）で追加列のみ、テーブル再作成はしない:

```sql
ALTER TABLE snapshot_articles ADD COLUMN featured_image TEXT;   -- D1 mediaId (26-char ULID) or NULL
ALTER TABLE snapshot_articles ADD COLUMN seo_json TEXT NOT NULL DEFAULT '{}';
  -- JSON: {title, description, canonical, noIndex, image}（mapper.ts の seo 形状と同一）
ALTER TABLE snapshot_articles ADD COLUMN locale TEXT;            -- v6 既存行は NULL、v7 capture 時は非 NULL（例: 'ja'）
ALTER TABLE snapshot_articles ADD COLUMN bylines_json TEXT NOT NULL DEFAULT '[]';
  -- JSON: string[]（解決済み byline slug 配列、または raw byline ID/slug 配列）
```

- **capture 側の強化**（`src/sync/snapshot/index.ts`）:
  1. **Stage 1 で `syncRemoteBylines()` を追加呼び出し**: `pullTaxonomies()` と並べて `syncRemoteBylines()`（1 GET、失敗時は `cache.getBylineMaps()` にフォールバック）を実行し、`cache.db` の `bylines` テーブルを最新化する。これによりオフライン時でも byline ID → slug 解決が機能する。
  2. **Stage 2 の抽出元と 0-GET 再利用の厳密化（穴 B 解消）**:
     - Clean published 記事（`!needsSingleGetForBody`）: 一覧の `rawObj` から `apiResponseToLocal(rawObj, { bylineIdToSlug })`（または `src/client/mapper.ts` の純粋抽出ヘルパ）で `featuredImage`, `seo`, `locale`, `bylines` を抽出（追加 HTTP 0 回）。
     - Draft / `published*` 記事で `syncStateClean && baseSnapshot`（0-GET 再利用）にヒットした場合: 一覧の `rawObj` はドラフトの古い作成時データしか持たないため、**`baseFm`（`readBaselineFrontmatter(baseSnapshot)`）から `featuredImage`, `seo`, `locale`, `bylines` を引き継ぐ**。
     - Draft / `published*` 記事で `prevSnapshot`（0-GET 再利用）にヒットした場合: **`prevSnapshot.locale !== null`（すでに v7 で capture 済み）のときのみ 0-GET 再利用**して `prevSnapshot` の 4 列を引き継ぐ（`prevSnapshot.locale === null` の v6 行だった場合は単一 GET へ進み v7 列を埋める）。
     - 単一 GET（`detailJson`）を実行した場合: `detailJson` から 4 列を抽出する。
- **v6 既存行と v7 空値の厳密な判別（穴 A 解消）**:
  - v7 capture は `locale` に必ず非 NULL 文字列（`frontmatter.locale || 'ja'`）を保存する一方、v6 からマイグレーションした未再 capture 行は **`row.locale === null`** となる。
  - したがって **`row.locale === null` のときのみ** v6 未 capture（劣化）と判定して `degradedFields: ['featuredImage', 'seo', 'locale', 'bylines']` を per-item warning に列挙し、`emit snapshot capture` の再実行を案内する。
  - **`row.locale !== null`（v7 capture 済み）の場合**は、`featuredImage === null` や `seoJson === '{}'` や `bylinesJson === '[]'` は「記事にアイキャッチや SEO・byline が設定されていない正常な空値」であるため、`degradedFields` には含めない（誤警告ゼロ）。
- **テスト**: `tests/migration_hash_invariants.test.ts` / `tests/cache.test.ts` パターン踏襲。既存 `sync_state.local_hash` および `base_snapshots.hash` が v6→v7 升级で不変であることを証明。

### 4.2 `pullFromSnapshot(options)` のフロー（単一 ULID / batch 共通コア）

```text
[0] ゲート: cache.getSnapshotMeta(collection) が null → ApiError(SNAPSHOT_NOT_AVAILABLE)
    captured_at が staleThresholdDays（既定 30、オプション調整可）超過 → 続行するが warning に [SNAPSHOT_STALE age=Nd]
[1] cache.getSnapshotArticle(id) / listSnapshotArticles(collection) を取得
    - targeted で MISS → ApiError(SNAPSHOT_MISS)「snapshot に存在しない（オフラインではリモート不在を証明できない）」
[2] Frontmatter 再構築（Layer A）:
    - isV6LegacyRow = (row.locale === null)
    - id, slug, title, collection, status, publishedAt, locale: row.locale || 'ja'
    - featuredImage: row.featuredImage ?? undefined
    - seo: JSON.parse(row.seoJson)（空オブジェクトなら省略）
    - bylines: JSON.parse(row.bylinesJson) を cache.getBylineMaps().idToSlug で解決
    - taxonomies: categoriesJson/tagsJson をパース（Layer A canonical スラッグ）
    - degradedFields:
      • isV6LegacyRow === true の場合: ['featuredImage', 'seo', 'locale', 'bylines']
      • row.taxonomyVerified === 0 の場合: 'taxonomies' を追加
      • row.bodySource === 'list-stale' の場合: 'body' を追加
[3] Markdown 合成:
    - hasDraftRevision = row.comparisonRev.includes('@draft:')
    - canonicalMarkdown = serializeMarkdown(frontmatter, row.bodyMarkdown, getTaxonomyCandidates(), { hasDraftRevision })
    - diskContent = localizeArticleMediaRefs(canonicalMarkdown, ...)（localMediaRefs 設定に従う）
[4] パス解決 & 既存ローカル編集保護:
    - resolveCanonicalArticlePath(...)（通常 Pull と同一。date prefix は existingSync / findLocalFilesByUlid から継承）
    - もし既存ファイルがディスク上にあり、!options.force かつ未プッシュのローカル変更がある場合は、
      通常 Pull（fast_path.ts:382-395）と同様にローカル変更を上書きせず localEditsPreserved: true で保護、
      または divergent 時は quarantineDivergentLocalCopies で posts/conflicts/ へ退避する。
[5] アトミック・コミット（commitArticleSnapshot 再利用 — Axis 6 完全遵守）:
    - commitArticleSnapshot(cache, workspaceRoot, {
        id: row.id,
        relPath,
        diskContent,
        canonicalContent: canonicalMarkdown,
        frontmatter,
        bodyMarkdown: row.bodyMarkdown,
        revForTransport: `snapshot:${row.comparisonRev}`, // 明示センチネル（Track 1 捏造ゼロ）
        revForComparison: row.comparisonRev,              // Track 2 比較キー
      })
[6] entries キャッシュ:
    - saveEntry({ ..., rev: `snapshot:${row.comparisonRev}`, rawJson: JSON.stringify({ source: 'snapshot', ... }) })
[7] 結果:
    - PullFromSnapshotResult { id, slug, status, filePath, updated, bodySource, degradedFields[],
      snapshotCapturedAt, warnings[] }
```

### 4.3 メディアの扱い（限定宣言）

- **バイナリ取得は一切行わない**（0 network calls 不変条件）。本文画像は `localMediaRefs` で既に `media/` にミラーされている分のみが相対パス化される。結果 warning に `[MEDIA_NOT_GUARANTEED] mirrored assets only; run pull-media when back online` を付与する。

### 4.4 Batch フォールバック（`emit pull --from-snapshot` の id 無指定時 — 穴 C 解消）

- `cache.listSnapshotArticles(collection)` の全行を **新しい順（`publishedAt ?? createdAt ?? ''` 降順、同値は `id` 降順）** にソートする。
- 通常 Pull（`listRemoteArticles`）と同一のウィンドウ解決（`resolvePostsSyncLimit`、既定 30）および `status` フィルタを適用する：
  - `status === 'all'`（既定）: **published 上位 `limit` 件 ＋ draft 上位 `limit` 件**（30+30 ウィンドウ）を選択（`--all` 指定時は全件）。
  - `status === 'published'` または `'draft'`: 該当 status の上位 `limit` 件を選択。
- **prune は実行しない**（snapshot は capture 時点の記録であり、disk prune の権威はオンライン remote walk のまま）。

## 6. status / diff / push / 次回オンライン pull との整合（Rev.2 確定設計）

1. **`status` / `diff` / `doctor` / `delete`（無改造で 100% 動作）**:
   - `pullFromSnapshot` が `commitArticleSnapshot()` で Layer A の `frontmatter`・`bodyMarkdown`・`hash` を `base_snapshots` に保存するため、`emit status`・`emit diff`・`emit doctor`・`emit delete`・`reconstructBaseline()` は **特別分岐なしでそのまま動作**する。オフラインで記事を編集して `emit diff` で差分確認するワークフローが即座に使える。
2. **`push`（`src/sync/push/guards.ts` での `PULL_REQUIRED_BEFORE_PUSH` ガード）**:
   - `src/sync/push/index.ts:121` から呼ばれる `evaluatePrePreflightGuards()`（`src/sync/push/guards.ts`）に `baseSnapshot` を渡し、`baseSnapshot?.rev.startsWith('snapshot:')` の場合は即座に `ApiError({ code: 'PULL_REQUIRED_BEFORE_PUSH', ... })` をスローする。
   - これにより、オンライン通常 Pull で実サーバーの Track 1 `_rev` を取得するまで、`snapshot:...` センチネルが `PUT { _rev }` に送られることは絶対にない。
3. **次回オンライン `pull` でのシームレス昇格（`src/sync/pull/fast_path.ts` デッドロック防止）**:
   - ユーザーがオンラインに復帰して `emit pull` を実行した際、リモート記事が snapshot 時点から更新されていない場合（`isSameRev(existingSync.remoteRev, remoteComparisonRev) === true`）、`tryFastPathOrHeal()`（`src/sync/pull/fast_path.ts:81`）が呼ばれる。
   - このとき `existingBase = options.cache.getBaseSnapshot(id)` の `existingBase?.rev.startsWith('snapshot:')` が `true` であれば、`tryFastPathOrHeal()` は `skipped: true`（ローカル未編集時）または `localEditsPreserved: true`（オフラインでローカル編集済み時）で返る直前に **`options.cache.saveBaseSnapshot({ ...existingBase, rev: remoteRev })` で Track 1 `remoteRev` へ昇格**させる。
   - これにより、**「① オフラインで `emit pull --from-snapshot` → ② オフラインで記事編集＆`emit diff` → ③ オンライン復帰後に `emit pull`（オフライン編集が保持されたまま `base_snapshots.rev` が実 Track 1 トークンへ昇格）→ ④ `emit push` 成功」** が `--force` 無しで完全に繋がる。

## 8. 検証計画（`tests/snapshot_pull.test.ts` 新規ほか）

1. **E2E オフライン復元 & 編集 → オンライン Pull 昇格 → Push**:
   - `captureWorkspaceSnapshot`（v7 4 列＋bylines 含む）→ ワークスペースファイル削除 → オフライン（`fetchFn` が呼ばれたら throw するモック）で `pullFromSnapshot(id)` → frontmatter（`featuredImage`, `seo`, `locale`, `taxonomies` Layer B, `bylines` slug）と本文が完全復元されること。
   - オフラインのまま `emit diff` / `inspectArticleDiff` が `synced`（編集後は `modified` + 正確な unified diff）を返すこと。
   - オフライン復元直後に `pushArticle` を呼ぶと `PULL_REQUIRED_BEFORE_PUSH` でブロックされ、ネットワーク PUT が 0 回であること。
   - オフラインで本文を編集した後、オンラインで通常 `pullArticle` を実行すると、**ローカルのオフライン編集が保持されたまま（`localEditsPreserved: true`）`base_snapshots.rev` が `'snapshot:...'` から実 Track 1 `remoteRev` へ昇格**し、続く `pushArticle` が成功すること。
2. **v6 劣化判定の正確性（誤検知ゼロ証明）**:
   - v7 で capture した `featuredImage: null`, `seo: undefined`, `bylines: []` の記事（`locale: 'ja'`）では `degradedFields` が空配列 `[]` になること。
