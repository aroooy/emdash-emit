# v0.1.61 Plan — Non-Blocking Window Prune: 「Abort」→「Skip & Warn」

**Status**: Implemented（v0.1.61）
**Target version**: 0.1.61（挙動変更。`postsSyncLimit` 窓プルーニングのみが対象で、schema migration なし）
**Authoritative specs touched**: `docs/sync-engine-and-revisions.md`（pullBatch 手順 4）、`docs/safety-guards-and-diagnostics.md`（FAQ Q1）、`README.md`（Unpushed Edits Safeguard の記述）、AGENTS.md §3 invariant 対応表

---

## 1. 問題定義（現状）

`emit pull`（バッチ）はスライディングウィンドウ（既定 published 30 + draft 30、`postsSyncLimit`）から押し出されたローカル記事のうち、リモートが削除済みまたは窓外のものを prune する。prune 前に各候補（および ULID 共有の重複ファイル）の未プッシュ編集を `isLocalFileUnmodified()` で検査し、1 件でも引っかかると:

- `src/sync/orchestrator.ts:362-378` が **`SyncPruneConflictError` を throw**（pull バッチ全体が中断）
- CLI: `src/cli/report-failure.ts:47` → `❌ <message>` + `process.exit(1)`
- MCP: `src/mcp/tool-errors.ts:250` → `isError: true` の tool error

### 現状の欠点

1. **巻き込み中断**: 未編集の窓外記事の正常 prune も、リモート記事の pull 完了も 1 件の未プッシュ編集で消える（throw が prune ループ前 `orchestrator.ts:377` で発火し、後続の pull worker プール自体が走らない）。
2. **AI エージェントワークフローの損傷**: MCP 経由では sync 全体が `isError: true` になり、Golden Path の `[0. SYNC WORKSPACE]` ステップが失敗扱いになる。エージェントは「再試行 or ユーザーへ質問」に fallback しがちで、本来成功している同期結果（taxonomy 同期・窓内記事の更新）を捨ててしまう。
3. **メディア側との非対称**: メディア prune はすでに同種の安全判断を **非ブロッキングな `pruneSkippedReason`** で表現している（`src/sync/media/pull_library.ts:217-230`, `src/sync/media/types.ts:192`）。incomplete walk のとき「削除しない + Layer 3 で理由を表示」であり、エラー throw はしない。記事 prune の Skip & Warn はこの前例の完全対称形。

## 2. 目的と安全性不変条件

**変更後**: 未プッシュ編集を持つ prune 候補は **prune 候補セットから除外（= ローカルファイルも `sync_state` もそのまま残す）** し、pull バッチは成功として完了、Layer 3（CLI/MCP）が警告を表示する。

安全性は現状と同等以上に保たれる:

- Abort 経路も Skip 経路も、**該当ファイルの unlink も `cache.deleteEntry()` も行わない**点は同一。Skip は「その候補だけを prune しない」であり、データ消失面はゼロ（むしろ他の clean 候補の正当な prune が復活する）。
- 「未プッシュ編集を絶対に消さない」原則（v0.1.28 で導入した保護）は不変。変わるのは _保護の表現形_（例外 → 結果フィールド + 警告）だけ。

## 3. 設計決定

### D1: エラー throw を `PullBatchResult.pruneSkipped` フィールドへ置換

`src/sync/orchestrator.ts`:

```ts
// PullBatchResult に追加
/** Window-out prune candidates kept on disk because they (or a ULID-sharing duplicate) have unpushed local edits. */
pruneSkipped?: UnpushedConflictItem[]; // 既存型 { id, slug, filePath } を再利用
/** Resolved batch window (resolvePostsSyncLimit result) so Layer 3 warnings report the true limit. */
windowLimit?: number;
```

- `orchestrator.ts:326-378` の検査ループは現状維持（候補ごと・重複ファイル込みの `isLocalFileUnmodified` 検査）。ただし結果の扱いを変える:
  1. 編集ありを検出した候補を `pruneSkippedArticles` に收集すると同時に、**`candidatesToPrune` から除去**する。除去は ULID 単位（canonical / duplicate どちらで検出されてもその ULID の候補は全除去 — 「片方だけ prune」は ULID 単位台帳と衝突するため）。
  2. `throw new SyncPruneConflictError(...)` を削除。後続の pull worker プールと prune ループ（`:431-470`）はそのまま走る。
  3. `return { ..., pruneSkipped: ..., windowLimit: limit }`（`pruneSkipped` は現状の `conflictItems` と同様にファイル単位、同一ファイルの重複なし）。
- **窓値の transport（レビュー指摘 1 対応）**: 警告文の `(currently: {limit})` に載せる `limit` は、**必ず orchestrator が解決済みの値（`:228` の `resolvePostsSyncLimit()` 結果）を `windowLimit` として result に載せて渡す**。CLI/MCP が個別に `ctx.config.postsSyncLimit` を参照すると、legacy `syncLimit` フォールバック等の優先順位（`src/utils/sync-limit-precedence.ts:58-67`）で orchestrator の実窓とズレうるため禁止。
- 警告文面（現 error message の「Why did this happen? / Recommended actions」）は Layer 3 formatter へ移す（D2）。orchestrator は事実のみ返し、文言を所有しない（presentation symmetry invariant に一致）。

### D2: 警告表示は共有 formatter（Layer 3）に新設

`src/presentation/article_report.ts` に `formatPruneSkippedArticlesNotice(items, limit)` を追加（メディア側 `formatPruneSkippedNotice()` の記事版。同一ファイルに並置し「なぜ沈黙せず明示するのか」のコメントも対称にする）:

```
🛡️ Pruning skipped for N file(s) belonging to M article(s) outside the sync window (currently: {limit})
because they have unpushed local edits. Their local files and cache entries were kept untouched.
  - posts/published/20190405_...-legacy-copy.md (slug)
Recommended actions:
  1. Push local changes:   emit push <filePath>
  2. Adjust sync window:   update "postsSyncLimit" in .emit/config.json if a larger window is needed
```

- CLI (`src/cli/commands/pull.ts` の `printBatchPullSummary()` 内、既存の 🛡️ preserved-edits 通知の直後) と MCP (`src/mcp/tools/sync-pull.ts` の batch 応答文字列、現 `preservedMsg` の隣) の**両方**がこの共有 formatter を呼ぶ（Axis 3 / presentation unification 準拠。`pull.ts` は `formatPruneSkippedNotice` を既に同 import 元から import 済み）。
- MCP 側は成功応答 (`✅ Synced ...`) に警告を追記するだけ。`isError: true` は発生しない。

### D3: `SyncPruneConflictError` の後方互換 — **export 維持（推奨）**

- v0.x ではあるが、`src/index.ts:50` が `orchestrator.js` を barrel export しており、`SyncPruneConflictError` は公開 façade の一部。AGENTS.md §5 の Ask First 対象（Public Facade 変更）でもあるため、**削除せず export のまま残す**ことを推奨:
  - クラス定義 (`orchestrator.ts:57-67`) と `src/index.ts` 経由の export はそのまま維持。
  - orchestrator 内から throw されなくなるので、`report-failure.ts:47` / `tool-errors.ts:250` の分岐は防御的フォーマッタとして**維持**（最小差分優先）。
  - `tests/layering.test.ts:74` の `ALLOWED_LAYER_2_SYMBOLS` エントリも変更しない（allowlist governance に抵触しない）。
  - CHANGELOG に「throw されなくなる（deprecated in behavior）」と明記し、v0.2 で移除検討と予告。

### D4: `--no-prune` / MCP `prune: false` は現状維持

明示的な prune オフは無警告のまま（ユーザーが既に選択済みのため）。Skip & Warn は「prune を試みたが候補を保護した」場合にのみ発火する（`pruneSkipped` が undefined なので自然に成立）。

## 5. リスク・論点

| 論点                                                 | 結論 / 対策                                                                                                                                                                                               |
| ---------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 窓外記事が無限に蓄積し disk/検索窓を圧迫するのでは？ | 警告にファイル一覧と `emit push` 誘導を含めるのでエージェントは即対応可能。蓄積自体は現行 Abort でも同じ（Abort は蓄積を止めず pull を止めるだけ）。                                                      |
| エージェントが警告を見落とすリスク                   | MCP は成功本文内に 🛡️ を必ず含む（メディア側 incomplete_walk と同じ確実性）。`emit status` の modified 表示が第二の網。                                                                                   |
| ULID 重複ファイルの半端な prune                      | 候補除去は ULID 単位（canonical + duplicate 全保護）で現状の「全有 or 全无」セマンティクスを維持。                                                                                                        |
| Public façade 変更（Ask First #3）                   | `PullBatchResult` は orchestrator facade の戻り値。**本 plan 自体が owner 承認依頼**であり、承認後に実装着手。既存フィールドは全て不変、追加のみ（`pruneSkipped?` と `windowLimit?` の 2 オプショナル）。 |
| `SyncPruneConflictError` removal を急がない          | D3 のとおり export 維持・throw ゼロ。削除は v0.2 で別途判断。                                                                                                                                             |
