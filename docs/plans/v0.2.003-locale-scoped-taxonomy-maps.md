# v0.2.3 実装計画書: ロケール別タクソノミーマップ（`byLocale`）による他ロケール同一スラッグ・ドラフト昇格漏れ修正

- **対象バージョン**: `v0.2.3`
- **作成日**: 2026-11-27
- **ステータス**: **実装済み（2026-11-27）**
- **前提**:
  - `v0.2.0` のロケール別タクソノミー構造（`categories/<locale>/*.yaml`, `tags/<locale>/*.yaml`）および `v0.2.1` の `drafts/<locale>/*.yaml` オフライン新設・自動昇格を前提とする。
  - `loadLocalTaxonomyMaps()` 等の既存の公開型・返却プロパティ（`slugToId`, `idToSlug`）の後方互換性を維持しつつ、多言語環境で同一スラッグ（例: `ai`, `emdash`, `development`）が別ロケール間でシャドウイングされる問題を構造的に解消する。

---

## 1. 背景・原因分析

### 1.1 現象

`categories/ja/` または `tags/ja/` に確定済みターム（例: `slug: ai`, `locale: ja`）が存在する状態で、別ロケール用の翻訳ペアタームをオフライン作成し：

```bash
emit new-term tag ai -l en -n "AI" --translation-of <ja_ulid>
```

英語記事（`locale: en`, `taxonomies: { tags: [ai] }`）を `emit push` しても、**`tags/drafts/en/` のドラフトがサーバーへ POST・昇格されず、`drafts/en/` に取り残されたまま正常終了（exit code 0）する**。

### 1.2 実コード上の原因（3 箇所の連動）

1. **`loadLocalTaxonomyMaps()`（`src/sync/taxonomies.ts:543-613`）のフラット構造**:
   - 全ロケールのタームを 1 つの `slugToId[kind]` にまとめて登録し、`compareTaxonomyTermDeterministically()`（`count` 降順 → ULID 降順）で **1 つの ID のみ**を保持している。
   - そのため、既存 `ja` ターム（特に `count >= 1`）が `slugToId.tag['ai']` を占有し、`drafts/en/` や `tags/en/` の同一スラッグをシャドウイングする。
2. **`promoteDraftTaxonomiesForArticle()`（`src/sync/push/taxonomy_plan.ts:209-210`）の解決漏れ**:
   - `taxonomyMaps.slugToId[kind]?.[term]` を引くため、`en` 記事であっても `ja` の既存 ID が返り、`draftById.has(resolvedId)` が `false` になって `drafts/en/` の昇格がスキップされる。
3. **`canonicalizeFrontmatterTaxonomies()`（`taxonomy_plan.ts:65`）および `syncArticleTaxonomies()`（`taxonomy_plan.ts:263-276`）でのクロスロケール誤紐付け**:
   - 両関数も `slugToId` をロケール無しで参照するため、仮にサーバー上に `ja` と `en` の両タームが存在しても、`en` 記事の `POST .../terms` に `ja` 側の ULID（`termIds`）が送信されてしまう。

### 1.3 着手前確認事項（Step 1 ゲート実測結果・2026-11-27）

- **検証内容**: `https://aroooy.net` 上で `ja` のみ存在するタグ（`emit-g4-gate-ja`）と `en` 下書き記事を作成し、`POST /_emdash/api/content/posts/{postId}/terms/tag`（`{ termIds: [jaTermId] }`）を送信。
- **実測結果**: **`200 OK` で成功**し、`GET /terms/tag` も `{ terms: [{ id: jaTermId, slug: "emit-g4-gate-ja", locale: "ja" }], entryLocale: "en", defaultLocale: "ja" }` を返却（一時リソースは削除済み）。
- **設計上の帰結（G4 段階導入の確定）**:
  - EmDash 本体は `entryLocale: "en"` の記事に対して `ja` ターム ID のフォールバック紐付けを**正当に受理する**（単一タグセットを多言語で共有する運用が今日成立している）。
  - したがって、Guard **G4（`knownTaxonomies`）をロケール限定へ厳格化（ハード拒否化）することは既存ワークスペースの回帰を招くため行わない**。
  - 代わりに、解決優先順位を **`byLocale[articleLocale]` 最優先 → 未存在時のみグローバルフォールバック** とし、`byLocale[articleLocale]` が非空かつ該当スラッグが別ロケールにのみ存在する場合は **非ブロッキング警告**（`emit new-term ... -l <locale>` の案内）を出す段階導入とする。

## 2. 機能別設計

### Layer 1: `loadLocalTaxonomyMaps()` への `byLocale` 追加（`src/sync/taxonomies.ts`）

1. **`TaxonomyMapPair` と `byLocale` フィールド追加（後方互換）**:
   - `loadLocalTaxonomyMaps(workspaceRoot)` の戻り値に `byLocale: Record<string, { slugToId: { category: Record<string, string>; tag: Record<string, string> }; idToSlug: { category: Record<string, string>; tag: Record<string, string> } }>` を追加する。
   - 従来のトップレベル `slugToId` / `idToSlug` はそのまま維持し、既存テスト・既存呼び出し元の破壊を防ぐ。
2. **ロケール単位での `toMaps()` 構築**:
   - `catItems` / `tagItems` を `(item.locale || '').trim().toLowerCase()` ごとにグルーピングし、各ロケールに対して独立に `toMaps()` を実行して `byLocale[locale]` を構築する。
   - これにより `Phase 2` の `aliasToIds`（人間可読名・デコード済みスラッグの一意性判定）もロケール内で独立するため、他ロケールの同名タームによるエイリアス衝突・シャドウイングも同時に解消される。
3. **共通解決ヘルパー `resolveTaxonomyTermId()` / `resolveCanonicalSlug()`（または `getLocaleScopedMaps()`）**:
   - 記事の `locale`（`parsed.frontmatter.locale?.trim().toLowerCase()`）が指定されている場合、`byLocale[locale]` を最優先で参照し、見つからない場合のみグローバル `slugToId` / `idToSlug` へフォールバックする（ULID 直接指定の `idToSlug` は一意なためグローバルフォールバックが安全に機能する）。

### Layer 2: `push/taxonomy_plan.ts` および `push/index.ts` のロケール一貫性

1. **`promoteDraftTaxonomiesForArticle()`（`src/sync/push/taxonomy_plan.ts`）**:
   - 記事ロケール `articleLocale = (parsed.frontmatter.locale || options.defaultLocale || 'ja').trim().toLowerCase()` を取得（`'ja'` ハードコードを避け `options.defaultLocale` へ統一）。
   - ターム解決時は `taxonomyMaps.byLocale?.[articleLocale]?.slugToId[kind]?.[term]` を最優先で参照する（さらに念のため、`draftById` 内の `draft.taxonomy === kind && (!draft.locale || draft.locale.toLowerCase() === articleLocale)` に対するスラッグ/エイリアス一致もフォールバック確認する）。
   - **インプレース更新のロケール対応（`taxonomy_plan.ts:171-186`）**:
     - `promoteTermWithAncestors()` 完了時、対象ドラフトのロケール `promotedLocale = (draft.locale || articleLocale).trim().toLowerCase()` に対応する `taxonomyMaps.byLocale[promotedLocale]` を必ず更新する（`idToSlug` の仮 ID 削除＋本 ID 登録、`slugToId` の正規スラッグ／エイリアス／`name` 差し替え）。
     - トップレベルの `taxonomyMaps.slugToId` / `idToSlug` についても、仮 ID が登録されていた箇所のみ本 ID へ差し替える（他ロケールの既存確定タームを上書きしないよう `=== oldId` ガードを徹底）。
2. **`canonicalizeFrontmatterTaxonomies()`（`src/sync/push/taxonomy_plan.ts:49-97`）**:
   - `parsed.frontmatter.locale` に基づき `byLocale[articleLocale]` を優先して `id`・`canonicalSlug` を解決する。
3. **`syncArticleTaxonomies()`（`src/sync/push/taxonomy_plan.ts:262-280`）**:
   - `resolvedTermIds` 解決時、`slugMap` として `taxonomyMaps.byLocale?.[articleLocale]?.slugToId[taxonomyName]` を優先使用する（未存在時のみグローバル `slugToId` へフォールバック）。
4. **Guard G4 (`knownTaxonomies` in `src/sync/push/index.ts:112-123`) — Step 1 ゲート反映**:
   - 既存のグローバル `knownTaxonomies` による G4 判定は維持し、単一タグセット共有ワークスペースの回帰を防ぐ。
   - `byLocale[articleLocale]` の対象タクソノミーが非空かつ指定スラッグが他ロケールにのみ存在する場合は、G4 ブロックせず **警告（`warnings`）** として `emit new-term <taxonomy> <slug> -l <articleLocale>` を案内する。

### 既知の Follow-up（非ブロッキング）

- `loadLocalTaxonomyCandidates()`（Layer B の `# <Name>` インラインコメント綴り）は依然グローバルで、同一スラッグ・別名タームがあると `count` 順で他ロケール名が選ばれうる（ハッシュ攪乱は無いが、見た目のコメントが他ロケール名になるケース）。今後の小改修でロケール別候補化を検討する。

## 5. 検証計画

1. **新規回帰テスト（`tests/offline_taxonomy_creation.test.ts` または `tests/locale_scoped_taxonomy_maps.test.ts`）**:
   - `categories/ja/`・`tags/ja/` に `slug: ai`（`count: 5`）が存在する状態で `emit new-term tag ai -l en -n "AI" --translation-of <ja_id>` を実行し、`locale: en` の記事を `emit push` した際：
     - `tags/drafts/en/` のドラフトがスキップされずサーバーへ `POST`（`translationOf: <ja_id>`, `locale: "en"`）されて `tags/en/` へ昇格すること。
     - `syncArticleTaxonomies()`（`POST .../terms`）に `ja` ではなく新設された **`en` ターム ID** が送信されること。
     - `ja` の既存 `ai` タームおよび `taxonomyMaps.byLocale.ja` が破壊・上書きされないこと。
   - `pushAll`（`ja` 記事と `en` 記事が混在し、両方に `slug: ai` が付いているバッチプッシュ）で、1 回の `loadLocalTaxonomyMaps()` 共有注入のまま `en` ドラフト昇格と両記事への正しいロケール別 ID 紐付けが成功すること。
   - `ja` にのみ存在するタームを `en` 記事（`tags/en/` に別タームが存在する状態）へ指定した場合に、G4 でハード拒否されず警告付きでフォールバック解決されること、および `tags/en/` が空（未整備）の場合もグローバル解決が通るアンカーテスト。
2. **全体ゲート**:
   - `npm run check && npm run build`（Prettier、`tsc --noEmit`、`check:cycles`、Vitest 全テスト・ビルド成功）
