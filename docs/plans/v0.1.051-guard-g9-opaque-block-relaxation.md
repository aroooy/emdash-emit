## 1. 背景と設計原則（3 分類＋単一バイパスフラグ）

現行の Guard G9（`src/sync/preflight.ts:781-793`, `src/client/portable-text.ts:1139-1147`）は、`verifyOpaqueBlocksUntampered(baseMarkdown, cleanedBody)` により「個数一致かつ各行完全一致」のみを許可し、**意図した削除・移動**や **画像レイアウト属性の軽微な調整**まで一律にエラーでブロックしている。

`v0.1.51` では変更内容を以下の **3 クラス** に厳密分類する：

| 分類                                       | 対象となる変更                                                                                                                                                                   | デフォルト動作（フラグ無し）                                | `--allow-modified-opaque-blocks` 指定時              |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- | ---------------------------------------------------- |
| **1. 安全な `image` 属性変更**             | `_type === 'image'` かつ変更が `SAFE_IMAGE_EDIT_KEYS`（`alignment`, `displayWidth`, `displayHeight`, `caption`, `title`, `alt`）のみ・構造キー不変・Zod 型検証通過               | **自動許可**（`PushResult.warnings` に変更通知を出力）      | 許可（同上）                                         |
| **2. 既存ブロックの純粋削除／並び替え**    | 残存ブロックが `base` ブロックと 1:1 対応し、JSON 無改変のまま一部が削除された場合、またはマッチ済みペアの相対順序が逆転（並び替え）した場合                                     | **許可（Warning 付き）**（`Removed ...` / `Reordered ...`） | 許可（Warning 付き）                                 |
| **3. 危険な改変・JSON 破壊・不正資産参照** | JSON 構文エラー、既存 `_key` / `asset` / `crop` / `hotspot` 等構造キーの変更、未知カスタムブロックの書き換え、新規追加 `image` ブロック内のローカル相対/`media/drafts/` パス参照 | **エラーでブロック**（`MODIFIED_OPAQUE_BLOCK`）             | **Warning に降格して許可**（`Bypassed Guard G9...`） |

> **フラグ意味の単一化**: `--allow-modified-opaque-blocks`（MCP: `allowModifiedOpaqueBlocks?: boolean`）は **「分類 3 の `MODIFIED_OPAQUE_BLOCK` エラーを Warning に降格して通過させる強制バイパス」** という 1 つの意味のみを持つ。

## 2. 詳細設計仕様

### 2.1 `inspectOpaqueBlockChanges()` の対応付けアルゴリズム（`src/client/portable-text.ts`）

既存の `verifyOpaqueBlocksUntampered(baseMarkdown, localMarkdown): boolean` は既存ユニットテスト（`tests/portable-text.test.ts:276-285`）互換のため **strict 仕様（削除＝`false`）のまま** 薄いラッパーとして維持し、**`preflight.ts` からは一切呼び出さない**。`preflight.ts` は詳細な差分検査を行う `inspectOpaqueBlockChanges(baseMarkdown, localMarkdown)` のみを呼び出し、`stripCodeBlocks` の二重スキャンを避けるため `extractOpaqueBlockLines` に統一する：

1. **フェンス抽出**:
   - `extractOpaqueBlockLines(baseMarkdown)` と `extractOpaqueBlockLines(localMarkdown)` でそれぞれ `<!--ec:block {...} -->` 行を抽出する。
2. **JSON パース検査**:
   - 各ローカルフェンスから JSON ペイロードを `JSON.parse()` する。構文エラーがある行は即座に `invalidJson`（分類 3: `'tampered'`）へ分類する。
3. **Multiset 対応の 1:1 対応付け（`_key` 優先 → 生文字列完全一致 → 同 `_type` 位置一致）**:
   - **Pass 1 (`_key` 一致)**: 非空文字列の `_key` を持つブロック同士を `_key` で 1:1 対応付ける（使用済みインデックス集合 `matchedBase` / `matchedLocal` で重複消費を防止）。
   - **Pass 2 (生文字列完全一致 — multiset)**: 未マッチのうち、`rawFence` が完全一致するペアを **1 対 1 で**（重複フェンスが複数あるギャラリー等を誤マッチしないよう消費しながら）対応付ける。
   - **Pass 3 (`_type` 位置一致)**: 未マッチのうち、同一 `_type` を持つペアを出現順に対応付ける（`_key` を持たないブロックの部分編集対応）。
   - ※ 本アルゴリズムにより、同じブロックを別の段落へ**移動**しても `_key`（または multiset 完全一致）で 1:1 対応付くため、誤って「削除＋追加」や改ざん扱いになることはない。さらに順序入れ替えの黙認を防ぐため、ステップ 6 で相対順序の逆転を `reorderedCount` として検知・Warning 出力する。
4. **Tier-1 ↔ Tier-3 遷移 & 新規 `added` ブロックのメディア参照検証（④・C 解消）**:
   - Tier-1 プレーン画像（`![alt](url)`）は Markdown 上に `<!--ec:block ... -->` を持たないため、Tier-1 の `alt` 編集は従来通り G9 対象外。
   - ユーザーが新規に `<!--ec:block {"_type":"image",...} -->` を手動追記した場合（`added`、base に対応なし）：
     - `push/media_stage.ts:225`・`media-refs.ts:143-146` は opaque fence をスキップするため、`media/drafts/...` や相対パス `../../media/...` を fence 内に書かれるとアップロード・正規化されずそのまま PUT されてしまう。
     - よって `added` な `_type === 'image'` ブロックは **`asset.url` のみ**を判定対象とし（`asset.src` やトップレベル `url` への曖昧なフォールバックは設けない）、`asset.url` が canonical root-relative URL（`/_emdash/api/media/file/...`）または `https://` / `http://` であることを必須とする。さらに `asset.storageKey`（非空文字列）が併記されている場合は、`asset.url` が `/_emdash/api/media/file/${storageKey}` プレフィックスと一致することも検証する。
     - 条件を満たさない場合（`asset.url` 欠落、相対パス `./` / `../` / `media/drafts/`、`storageKey` 不一致等）は **分類 3（`'tampered'` / `MODIFIED_OPAQUE_BLOCK` エラー）** としてブロックする（エラーメッセージで「ローカル下書き画像は `![alt](../../media/drafts/...)` を使うか canonical URL を指定する」旨を案内）。なお `collectArticleStorageKeys()`（`src/sync/media/body_scan.ts:61-82`）が opaque fence 内の `/_emdash/api/media/file/<storageKey>` も拾うため、canonical URL 強制はメディアミラーリングおよび pruning 保護とも自動的に整合する。
5. **安全 `image` 属性の Zod 検証 & `_key` 一貫性（① 解消）**:
   - ホワイトリスト: `SAFE_IMAGE_EDIT_KEYS = ['alignment', 'displayWidth', 'displayHeight', 'caption', 'title', 'alt']`
   - `_key` の扱い（矛盾解消）:
     - `base` に非空 `_key` がある場合、`local._key` は `base._key` と一致必須（勝手な `_key` 書き換えは分類 3）。
     - `base` に `_key` が無い場合（Pass 3 で対応付け）、`local._key` の不在または新規非空文字列は許容する。
   - その他の構造キー（`_type`, `asset`, `crop`, `hotspot`, 未知キー等）は `base` と deep-equal（キー順正規化比較）で一致必須。
   - Zod スキーマ検証（`tests/portable-text.test.ts:146, 205` で実測済みの文字列型に加え将来の inline span 配列にも対応）:
     - `alignment`: `z.string().nullable().optional()`
     - `displayWidth` / `displayHeight`: `z.union([z.number(), z.string()]).nullable().optional()`
     - `caption`: `z.union([z.string(), z.array(z.unknown())]).nullable().optional()`
     - `title` / `alt`: `z.string().nullable().optional()`
     - 型不正は分類 3（`'tampered'`）へ落とす。
6. **削除・並び替えの純粋性（A 解消）**:
   - 未マッチの `base` ブロックが存在する場合、それらを `removedCount`（分類 2）としてカウントし、Warning 付きで許可する。
   - 1:1 マッチしたペア集合 `matchedPairs` を `localIndex` 昇順に並べたとき、`baseIndex` 列が狭義単調増加でない場合（`matchedPairs.length - LIS(baseIndices)` を `reorderedCount` として算出、少なくとも 1 ブロック以上の相対順序逆転がある場合は `reorderedCount > 0`）、分類 2 と同一に「並び替え」の Warning を出力して許可する（黙って無警告通過させない）。

## 5. 今後の拡張候補（`v0.1.52` 以降）

- **新規追加された非 `image` カスタムブロックへの Warning**: 現状 `added` チェックは `_type === 'image'` の `asset.url` 検証のみを行っており、手書き追加された未知カスタムブロック（例: `core:callout`）は無警告で通過する。次版では `addedCustomCount` として `Added N <!--ec:block ... --> custom block(s) not present in baseline.` の Warning を出力することを検討する。
