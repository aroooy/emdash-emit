## 1. 背景と目的

### 1.1 現状の既知の制限（実測根拠）

`emit pull --from-snapshot`（v0.1.54、`src/sync/pull/snapshot_pull.ts`）は 0 network calls で記事 Markdown を復元するが、**メディアバイナリは一切保証しない**。全局 warning に `[MEDIA_NOT_GUARANTEED] mirrored assets only; run pull-media when back online`（`snapshot_pull.ts:382-384`）を付与する設計上明示された制限である。

| 事実 | 根拠 |
| --- | --- |
| `snapshot_media` テーブルはメディア**メタのみ**（バイナリ非保持、Schema v6 設計思想「0 binary downloads」） | `migrations.ts:212-230`、`snapshot/index.ts` Stage 3 |
| スナップショット復元後の本文画像参照（`localMediaRefs` により `../../media/<storageKey>` にローカライズ済み）は、`media/` に実体が無いとリンク切れ | `docs/media-pipeline.md` §4 |
| スナップショット時点の全 storageKey とサイズ一覧はオフラインで参照可能（`listSnapshotMedia()`） | `db/cache.ts:889` |
| 本文→storageKey 抽出は既存（標準画像・HTML img・`<!--ec:block -->`・legacy `[dimage]` 対応） | `media/body_scan.ts` `collectArticleStorageKeys()` |
| 「既にミラー済みなら 0-HTTP 短絡」の先行実装あり | `docs/media-pipeline.md` §5.1、`pull/media_stage.ts` |

**ユーザーペイン**: 機内・移動中等の完全オフラインで過去記事をスナップショット復元しても、Obsidian / VS Code のプレビューで画像が表示されず、「写真配置を確認しながら追記・修正する」フローが成立しない。

### 1.2 目的

オプトインで **メディアバイナリのローカルキャッシュ層**を導入し、オフラインの `emit pull [target] --from-snapshot` 実行時に、復元対象記事が参照するメディアをワークスペース `media/` へ自動展開（0-HTTP・0-GET）する。これにより `--from-snapshot` の中核ユースケース（オフライン執筆）をテキストだけでなく画像込みで完成させる。

### 1.3 要望案の評価と本計画での改訂点

要望が提示した 3 案のうち、**案1（cache.db 内 BLOB）・案2（専用別 DB）は却下**（巨大 DB 化・VACUUM なしで縮まない・BLOB 読出し→デコード→書込の展開コスト）。**案3（ファイルシステムキャッシュ）を採択**するが、要望原文のままではなく以下を改訂して採用する。

| # | 要望原文（案3） | 本計画での改訂 | 理由 |
| --- | --- | --- | --- |
| R1 | キャッシュ配置 `.emit/cache/media/<storageKey>` | **`media/_cache/<basename(storageKey)>`**（ワークスペース `media/` 配下の専用サブディレクトリ） | ミラー所在を前提とする診断系（`sync_media_search` の mirrored 判定、doctor `--check-media-library` の `countMirroredMedia(mediaDir)`、pruning、G20）が走査する `media/` ツリーに含めず、既存「ミラー＝`media/<markdownRef>.<ext>`」モデルを一切汚染しない。`.emit/` 配下は gitignore 済みだが診断系から完全不可視となり隠れたディスク消費になるため、`media/_cache/`（Git 対象・`_trash/` と同様の予約ディレクトリ）として可視性を確保する |
| R2 | ハードリンク（`fs.linkSync`）または CoW（`COPYFILE_FICLONE`）で展開 | **フォールバックチェーン: `linkSync` → `copyFile(COPYFILE_FICLONE)` → 通常 copy** | Windows 非 NTFS・クロスボリューム（`EXDEV`）で link が失敗しうるため、必ず copy に落ちる。実体は常に 2 系統（キャッシュ＋ミラー）存在しうるので「削除されてもキャッシュ本体は保護される」性質はリンクに依存しない |
| R3 | 「storageKey はイミュータブル＝コンテンツアドレス、検証不要」 | **展開時に `snapshot_media.size` と `fs.statSync().size` を突合**（SHA-256 は任意） | R2 基盤（R2 ストレージ）側の正しさをクライアント側で無条件信頼しない。サイズ不一致は破損とみなし `[MEDIA_CACHE_CORRUPT]` 警告 + 当該キーをスキップ（オンライン復帰後の再取得へ委ねる）。ハッシュ突合は opt-in |
| R4 | キャプチャ時にメディア実体を無制限に一緒に取得 | **上限必須**: `snapshotMediaLimit`（既定 200 件）+ `snapshotMediaMaxBytes`（既定 512 MiB）の予算で打ち切り、打ち切り時は `[MEDIA_CACHE_BUDGET] cached X/Y` warning | フリート規模ライブラリ（数千ファイル）への無制限ダウンロードを防止。`mediaSyncLimit` と同思想の epistemic な境界宣言 |
| R5 | 要望は展開のみ言及、キャッシュ削除手段なし | **prune + GC**: `emit snapshot --clear` で manifest 行を削除し、**参照ゼロのキャッシュ実体を即座に `fs.unlinkSync()` で解放**。加えて孤児実体のクリーンアップフラグ `--prune-cache` | DB BLOB と違いファイルシステムキャッシュは unlink で即 OS ストレージ解放できる（要望 §3 の案3 の利点をそのまま実装に反映） |

## 2. 設計原則（4 つの不可侵ルール）

1. **オプトイン厳格**: キャッシュ書込は `emit snapshot --include-media` / `sync_snapshot(includeMedia: true)` / `.emit/config.json` の `"snapshotMedia": true` のいずれかが有効なときだけ発生する。デフォルト（false）のユーザーには一切のオーバーヘッド・ディスク消費を与えない。`.emit/config.json` への永続化は **CLI のみ**（MCP tools は config を変更しない — Invariant 2 と対称）。
2. **キャッシュ＝Emit 所有の派生データ**: `media/_cache/` 配下はユーザー編集対象ではない。ワークスペース側（`media/<markdownRef>.<ext>`）の削除・破損・編集はキャッシュ本体に決して波及しない（実体は常に 2 系統を維持する展開経路のみ使用 — R2）。既存ミラーが既にある場所へは**絶対に上書きしない**。
3. **Epistemic 宣言**: 展開結果は常に `[MEDIA_CACHE captured_at=<ISO> restored=N missing=M skipped=K]` で報告し、manifest に無いキーを「リモートに存在しない」と断定しない（キャッシュ不足＝取得漏れの可能性であり、オンライン復帰後の `pull-media` で解消）。
4. **0 network calls 不変条件**: `--from-snapshot` の展開パスは認証トークン無しで動作し、fetch を一度も呼ばない。manifest は `.emit/cache.db`（Schema v8）のみから読む。

## 3. キャッシュ構造（案3 改訂版: Content-Addressable Filesystem Cache）

### 3.1 ディスク配置

```text
<workspace>/
  media/
    <markdownRef>.jpg          ← 既存ミラー（従来どおり、変更なし）
    <markdownRef>.yaml         ← 既存 companion（従来どおり）
    _trash/                    ← 既存の削除退避（v0.1.53）
    _cache/                    ← ★新規: Emit 所有のオフラインキャッシュ（予約名）
      01HZ...abc.jpg           ← ファイル名 = basename(storageKey)（＝コンテンツアドレスキー）
      01HZ...def.png
```

- **キー**: `basename(storageKey)` をそのままファイル名に使用（`storageKeyToMarkdownRef` の sanitize は**通さない** — storageKey は `VALID_MEDIA_FILE_KEY`（`utils/media-refs.ts:38-39`）で `[0-9A-HJ-NP-Z]{26}(\.<ULID>)*\.(jpg|…)` を満たすため、パス traversal・隠しファイル・不正名は形式検証で構造的に排除。basename は storageKey と 1:1 対応するため衝突しない）。
- **★C3（Rev.2）— slash 付き移行コーパスの明示的除外**: `docs/media-id-spaces.md` が「migrated corpora may use any path such as `uploads/2026/11/sample.png`」と定義する slash 付き storageKey は、`VALID_MEDIA_FILE_KEY` を**満たさないためキャッシュ対象外**（basename 抽出時に別ディレクトリの同名ファイルが衝突するため、slash を潰したフラット名は採用しない）。これらのキーは `body_scan.ts` の参照収集（`(?:^|/)media/file/`）で拾われる一方キャッシュに存在しないので、§4.3 の missing カウントに入り `[MEDIA_NOT_GUARANTEED]` に自然フォールバックする。移行コーパスのオフライン保証は本リビジョンの**宣言済み非スコープ**であり、オンライン復帰後の `pull-media`（companion-backed ミラー）で解消する。
- **イミュータブル前提**: R2 の storageKey は不変（`docs/media-id-spaces.md`）。同一キーの実体は一度書いたら書き換えない（再取得も上書きしない。破損復旧は delete → 次回 capture で再生成）。

### 3.2 Manifest（Schema v8: `snapshot_media` 拡張）— Ask First・カテゴリ2

`CURRENT_CACHE_SCHEMA_VERSION: 7 → 8`。既存の「`PRAGMA table_info` + 条件付き `ALTER TABLE`」パターンで追加列のみ（v7 migration と同型、テーブル再作成なし）:

```sql
ALTER TABLE snapshot_media ADD COLUMN cached_at INTEGER;      -- NULL = 未キャッシュ
ALTER TABLE snapshot_media ADD COLUMN cache_path TEXT;        -- 'media/_cache/<basename>' (workspace-relative)
ALTER TABLE snapshot_media ADD COLUMN content_hash TEXT;      -- 'sha256:<hex>'（取得時に計算、任意検証用）
```

- **マニフェストの所在**: `snapshot_media` 行そのものが manifest を兼ねる（メディアは site-wide・collection 非依存 — v6 設計を踏襲）。実体ファイルの有無判定は要望どおり `fs.existsSync(cache_path)` のみで O(1)（差分スキップは §4.2 で実装）。
- **クリア整合**: `clearWorkspaceSnapshot()` は既存規則（`snapshot_meta` 最終行削除時に `snapshot_media` を全消去、`cache.ts:977-980`）に従うが、**v8 ではこれに加えて collection 非依存の残存 `cached_at IS NOT NULL` 実体を GC 対象として列挙**する（§3.4）。

### 3.3 Layer 0 ヘルパ（新規 `src/utils/media-cache.ts`）

- `mediaCacheDir(mediaDir): string` = `path.join(mediaDir, '_cache')`
- `isReservedMediaSubdir(name)` = `_trash` | `_cache` の判定（既存スキャン側の除外リストと共有する単一の真実）
- `toMediaCacheFileName(storageKey): string | null` — `VALID_MEDIA_FILE_KEY` 検証 + basename 抽出。slash 付き移行コーパス等は不合格 → `null`（★C3: 呼び出し側は `null` を「対象外キー」として silently スキップし、missing カウントへ回す）
- `resolveSnapshotMediaOption(explicit, config)` — `localMediaRefs` と同一の precedence パターン（明示引数 > `.emit/config.json`、純関数・I/O ゼロ）。永続化は CLI の `resolveAndPersistSnapshotMedia()` のみ

### 3.4 キャッシュ GC 規則（Rev.2: C2・C5 確定）

| トリガ | 挙動 |
| --- | --- |
| `emit snapshot --clear` | **順序保証（★C2）**: `collectWorkspaceArticleStorageKeys()` で参照集合を収集 → `cache.clearSnapshot(collection)` の**前**に実行する。`clearSnapshot()` は `snapshot_articles` を DELETE するため、後では snapshot 本文基準の参照保護ができず、復元予定記事が参照するキャッシュ実体を誤解放する |
| ↳ GC 対象 | ワークスペース本文（`draft/`・`published/`・`conflicts/`）と snapshot 本文の**いずれからも**参照されない `cached_at IS NOT NULL` 実体を `fs.unlinkSync()` で即時解放。参照中有の実体は `[MEDIA_CACHE_PRESERVED]` として件数のみ報告 |
| ↳ site-wide GC 条件（★C5） | `snapshot_media` は collection 非依存（site-wide）であり、`cache.ts:977-980` の既存規則どおり**残存 `snapshot_meta` が 0 件のときのみ** `snapshot_media` 行を消去する。複数 collection 運用で 1 つだけ `--clear` した場合は `snapshot_media`（manifest）が有効なままなので、**バイナリ GC も行わない**（他の collection の復元が壊れるため）。全 collection の meta が消えた時点で manifest + バイナリの完全 GC が走る |
| `emit snapshot --prune-cache` | manifest に無い（孤児化した）`media/_cache/` 実体の削除。manifest 上有効なキーは保持 |
| ワークスペース側ミラーのユーザー削除 | **何もしない**（キャッシュ本体は保護。次回 `--from-snapshot` 展開で再生成される） |

**★C2 — 参照収集ヘルパの配置（Layering gate 対応）**: `iterWorkspaceArticles` は Layer 2 の `src/sync/workspace/` にあり、`sync/snapshot/index.ts` の許可 sibling は `['../media/index.js', '../pull/index.js']`（`tests/layering.test.ts:304`）のみで `../workspace/index.js` は含まれない。一方 **`src/sync/media/prune_protect.ts` は既に `iterWorkspaceArticles` を import 済み**（`:25`）で、ワークスペース本文×`collectArticleStorageKeys()` の合成ループ（`:89-101`）が実在する。そのため参照収集は **`prune_protect.ts` に `collectWorkspaceArticleStorageKeys(workspaceRoot, collection): Set<string>` として新設**し、`snapshot/index.ts` は既存の許可済み `../media/index.js`（prune_protect は barrel re-export 済み）経由で呼ぶ。**新規 sibling エッジは不要**。

## 4. パイプライン変更

### 4.1 Snapshot capture（オンライン・差分更新、`src/sync/snapshot/index.ts` Stage 3 拡張）

```text
[Stage 3] メタデータ walk（従来どおり、fetchMediaListPage のページ単位）
   └─ ★新規 Stage 3b: includeMedia 有効時、walk 済みレコードからダウンロード候補を決定
       候補条件: storage_key 非 NULL ∧ VALID_MEDIA_FILE_KEY 合格 ∧ fs.existsSync(cache_path) === false（0-GET スキップ判定）
                 ∧ ワークスペース media/ に companion-backed ミラーが既に在るキーは
                   「キャッシュ不要の済みアセット」としてスキップカウント（既存ミラーの再下载ゼロ）
       予算: snapshotMediaLimit 件 / snapshotMediaMaxBytes バイトに達した時点で打ち切り
                 → [MEDIA_CACHE_BUDGET cached=X/Y] warning、残りは次回 capture の差分取得へ
       並列度: 既存 concurrency レーラを再利用。各ファイルは GET /_emdash/api/media/file/<storageKey>
       書込手順: tmp ファイル（media/_cache/.tmp-<key>）へ書込 → size === snapshot_media.size 突合
                 → sha256 計算 → rename → manifest 更新（cached_at, cache_path, content_hash）
```

- **差分更新の容易さ**（要望 §3 の案3 利点）: 2 回目以降の capture は既存実体の `fs.existsSync` + manifest で 0-GET スキップ。新規メディアのみをネットワーク取得する。
- `SnapshotCaptureResult` に `mediaCached: number; mediaCacheSkipped: number; mediaCacheBytes: number; mediaCacheBudgetHit: boolean` を追加（公開シグネチャ変更 — Ask First・カテゴリ3）。

### 4.2 オフライン展開（`--from-snapshot`、`src/sync/pull/snapshot_pull.ts`）

**★C1（Rev.2）— import 経路の確定**: `collectArticleStorageKeys()` は Layer 2 の `src/sync/media/body_scan.ts` にあり、`ALLOWED_LAYER_2_SIBLING_IMPORTS`（`tests/layering.test.ts:299-305`）で `pull/` 配下に許可された `../media/index.js` エッジは **`sync/pull/media_stage.ts` のみ**。`snapshot_pull.ts` に直接 import を追加すると Layer 2 sibling gate で失敗する。そのため展開処理本体（Stage 7）を **`src/sync/pull/media_stage.ts` のエクスポート関数 `restoreSnapshotReferencedMedia()`**（同ファイルは既に `collectArticleStorageKeys` を import 済み・`:42`）として置き、`snapshot_pull.ts` は同一ディレクトリの `./media_stage.js` から呼ぶ（自己ディレクトリ相対は sibling coupling の対象外 — `pull/quarantine.ts` を import 済みの既存パターンと同型）。**Allowlist / Sibling Snapshot は無変更で成立する**。

```text
[既存 Stage 0-6] の記事復元フローはそのまま。★新規 Stage 7: Materialize Referenced Media（media_stage.ts 実装）
[7a] 復元した各記事の diskContent + row.bodyMarkdown から collectArticleStorageKeys() で storageKey 集合を収集
     （frontmatter featuredImage は D1 mediaId → snapshot_media.media_id 参照で storage_key を解決）
     ★C3: toMediaCacheFileName() が null を返す slash 付き移行キーは対象外 → missing カウントへ（§3.1）
[7b] 各キーについて:
     1. ワークスペース media/ に companion-backed ミラーが既に存在 → no-op（既存ミラー優先、上書きゼロ）
     2. media/_cache/<basename> 実体あり ∧ size === snapshot_media.size → 展開:
        fs.linkSync(cacheFile, mirrorPath)          // APFS/ext4/NTFS 同一ボリュームで瞬時・容量ゼロ
          └ EXDEV/EACCES/EPERM → fs.copyFileSync(FICLONE) → 通常 copyFileSync（R2 フォールバックチェーン）
        + companion media/<stem>.yaml を snapshot_media メタから合成（filename/mimeType/size/alt/caption/
          storageKey/url/status: 'ready'、id は snapshot_media.media_id — 「所有権の真実は companion id:」不変条件遵守）
        + cache.saveMediaState({ status: 'ready', workspacePath, markdownRef, ... })（既存 0-HTTP 短絡インデックスと対称）
     3. size 不一致 → スキップ + [MEDIA_CACHE_CORRUPT key=<storageKey>]（オンライン復帰後 pull-media で修復）
     4. 実体なし → missing カウント（warning は §4.3 の統合宣言へ集約）
[7c] per-item: restored/missing/skipped を PullFromSnapshotResult.mediaRestored / mediaMissing に記録
```

- **`localMediaRefs: false` ワークスペース**: 本文は canonical URL のままなので展開した画像は本文から参照されないが、`media/` への実体展開は**行う**（Obsidian 等のプレビュー設定に依存しない実体保証。warning で「本文参照は canonical URL です」と補足）。

### 4.3 `[MEDIA_NOT_GUARANTEED]` の後方互換的再定義（重要）

要望 §6 の期待どおり、キャッシュ充足時は警告自体を出さない:

- **全参照キーが解決済み**（既存ミラー or キャッシュ展開成功）→ `[MEDIA_CACHE restored=N]` の info 宣言のみ。`[MEDIA_NOT_GUARANTEED]` は**出力しない**。
- **1 つでも missing/corrupt あり** → 従来どおり `[MEDIA_NOT_GUARANTEED] mirrored assets only; run pull-media when back online` を併記（既存テスト `snapshot_pull.test.ts:243` の期待は「解決不能キーがあるケース」で維持される）。
- キャッシュ機能が無効（manifest にキャッシュ行が無い / `media/_cache/` 不在）→ 完全に v0.1.54 と同一の挙動（無効ユーザーへの影響ゼロ）。

### 4.4 オンライン復帰後の昇格との整合（v0.1.54 設計のまま、変更なし）

- キャッシュ展開で生成した companion・`media_state` は通常 pull の「0-HTTP 短絡」条件（companion `id:` + size 突合）を満たすため、オンライン復帰後の `emit pull` は**再ダウンロード 0 回**でミラー確認済み扱いになる。
- `snapshot:` sentinel → Track 1 昇格（`fast_path.ts`）・`PULL_REQUIRED_BEFORE_PUSH` の流れは v0.1.54 のまま無変更。オフライン中に展開画像を参照した既存記事を編集して push する経路も、本文 URL は canonical storageKey を保持するため G5/G11（ローカル draft 画像の自動アップロード）を発火させない — **新規 guard 不要**である旨をテストで固定する。

## 5. CLI / MCP インターフェース

| 層 | 仕様 |

## 8. 検証計画

1. **オフライン往復 E2E（中核）**: オンラインで `snapshot capture --include-media` → ワークスペースの `media/` と記事ファイルを削除 → fetch が呼ばれたら throw するモック下で `pullFromSnapshot(id)` → 本文画像が `media/<markdownRef>.<ext>` に実在し、companion `id:` が D1 mediaId と一致、`media_state.status === 'ready'`、`[MEDIA_CACHE restored=N]` が付き **`[MEDIA_NOT_GUARANTEED]` が出力されない**こと。
2. **差分 0-GET**: 2 回目 capture で既存キャッシュ実体に対する GET が 0 回（fetch モックの URL 記録で証明）、新規キーのみダウンロードされること。
3. **予算打ち切り**: `snapshotMediaLimit=2` / `maxBytes` 超過時に `[MEDIA_CACHE_BUDGET]` 警告と正確な cached=X/Y、次回 capture で残りが取得されること。
4. **フォールバックチェーン**: `linkSync` を throw させる fs モックで FICLONE→copy に落ち、最終ミラー実体の sha256 がキャッシュ実体と一致すること（POSIX テスト環境で link 失敗パスを意図的に再現）。
5. **破損検知**: キャッシュ実体を切り詰めて size 不一致 → `[MEDIA_CACHE_CORRUPT]` + スキップ + `_cache` 実体は変更されないこと。
6. **診断系不変**: `doctor.ts:684` の unattributable media 誤警告が `_cache/` 混入時にゼロであること（★C4）、`countMirroredMedia` / `collectLocalMediaMirrorCandidates` / pruning / G20 が `_cache/` を無視すること（各既存テストに `_cache` 混入ケース追加）。`--clear` GC が参照中有実体を保持し参照ゼロ実体を unlink すること。
7. **★C2 — GC 順序と site-wide 条件**: `--clear <collection>` が `snapshot_articles` DELETE **前**に参照収集を完了していること（削除後に収集したケースを模したテストで誤解放しない）、および別 collection の `snapshot_meta` が残る限り manifest・バイナリとも GC されないこと。
8. **★C3 — slash 付き移行キー**: storageKey が `uploads/2026/11/sample.png` 形式の記事に対し、キャッシュ取得候補から除外され（capture 時 GET ゼロ）、`--from-snapshot` 展開では missing カウント → `[MEDIA_NOT_GUARANTEED]` にフォールバックすること。
9. **後方互換**: `snapshotMedia` 無効ワークスペースは v0.1.54 と同一出力（`[MEDIA_NOT_GUARANTEED]` 常に付き、fetch ゼロ）。Schema v7→v8 で `local_hash` / `base_snapshots.hash` 不変（`migration_hash_invariants`）。
10. **push 安全**: オフライン展開済み記事の編集 → オンライン pull 昇格 → push が成功し、`media/drafts/` 自動アップロード系 guard（G5/G10/G11）が発火しないこと。
11. **品質ゲート**: `npm run check`（format/typecheck/cycles/test）100% Green、Axes 0–9・Rules 1–5 green。**`ALLOWED_LAYER_2_SIBLING_IMPORTS` のスナップショットは無変更であること自体を gate で証明**（★C1/C2 の配置設計が壊れた場合に検知される）。
