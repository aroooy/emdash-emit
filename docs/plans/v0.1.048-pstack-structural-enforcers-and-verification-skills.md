## 1. 背景と目的（なぜ `pstack` を Emit に導入するのか）

`pstack` の中核原則 **`encode-lessons-in-structure`** および **`/correct`** は次の前提に立っています：

> _「すべてのコントリビュータ（AI エージェント）は、開いたファイルだけを見て、一番近くの例をコピーし、コンパイルが通る最短経路を取ると仮定せよ。ドキュメントや `AGENTS.md` に文章のルールを書き足すのは最後の手段であり、エージェントが読み飛ばしても何も失敗しないルールは必ず再び破られる。」_

また **`/interrogate`** および **`prove-it-works`** は、AI レビューにおけるノイズ（ハルシネーションや推測による誤指摘）を排除するため、次のルールを課します：

> _「レビュー指摘は、実コードに対する実行（失敗するテスト、再現コマンド、または実ファイル・実型の検証出力）で証明されたものだけが生き残る。実行していない推測はすべて破棄（Drop）せよ。」_

### 事前コード監査（`/correct` Step 1）で実際に発見された「文章ルールと実装の乖離」

本計画の作成にあたり、現行 `v0.1.47` コードベースに対して `AGENTS.md` §3（Top 7 Principles）の遵守状況を静的監査した結果、**「`AGENTS.md` に明記されているが静的テスト（Enforcer）が存在しなかったために発生していた乖離」が 2 件** 発見されました：

1. **乖離 1（Invariant 5: Lenient Parse Alignment の漏れ）**:
   - `AGENTS.md` §3 Principle 5 は _「すべての読み取り専用・検査系モジュール（`status`, `doctor`, `conflicts`, `delete`, `article_search/local`, `media/body_scan`）は `parseMarkdownLenient()` を通してパースしなければならない」_ と規定している。
   - しかし実際には [src/sync/delete.ts](file:///Volumes/ext/github/emdash-emit/src/sync/delete.ts#L134) と [src/sync/diff.ts](file:///Volumes/ext/github/emdash-emit/src/sync/diff.ts#L74) が厳格な `parseMarkdown()` を直接呼んでおり、クォート漏れ（`%e6%9c%aa%e5%88%86%e9%a1%9e` 等）を持つ `healable` な記事に対して `emit delete` やファイル名 ULID 欠落時の `emit diff` を実行すると修復不能なエラーで落ちる状態になっていた。
2. **乖離 2（Invariant 7: CLI Action Failure Presentation の漏れ）**:
   - `AGENTS.md` §3 Principle 7 は _「すべての CLI アクションはエラーを `reportActionFailure()` にルーティングし、生のスタックトレースを出してはならない」_ と規定している。
   - しかし実際には [src/cli/commands/status.ts](file:///Volumes/ext/github/emdash-emit/src/cli/commands/status.ts) 内の 3 コマンド（`emit status` [L109](file:///Volumes/ext/github/emdash-emit/src/cli/commands/status.ts#L109)、`emit diff` [L245](file:///Volumes/ext/github/emdash-emit/src/cli/commands/status.ts#L245)、`emit init` [L319](file:///Volumes/ext/github/emdash-emit/src/cli/commands/status.ts#L319)）に `try / catch (err) { reportActionFailure(err); }` が無く、不正な `--profile` 指定や `[CACHE_SCHEMA_MISMATCH]` 発生時に生のスタックトレースが露出する状態になっていた。

`v0.1.48` では、これらの乖離を修正すると同時に、**ステップ A（構造的強制ゲート Axes 6–9 の実装 + `AGENTS.md` Rule ⇔ Enforcer 表）** と **ステップ B（`.agents/skills/` への `pstack` 流 3 大スキル `/interrogate`・`/correct`・`/blast-radius` の導入）** を実施します。

### 2.2 事前監査で見つかった既存コード乖離 2 件の是正

1. **[src/sync/delete.ts](file:///Volumes/ext/github/emdash-emit/src/sync/delete.ts#L134) & [src/sync/diff.ts](file:///Volumes/ext/github/emdash-emit/src/sync/diff.ts#L74) の `parseMarkdownLenient` 対応**:
   - `src/sync/delete.ts`: `const parsed = parseMarkdownLenient(rawContent, targetFile) ?? parseMarkdown(rawContent, targetFile);` に変更。これにより、クォート漏れ等の `healable` な frontmatter を持つローカルファイルでも `isLocalFileUnmodified()` 判定および `emit delete` が正常に動作する（完全に壊れた YAML の場合のみ従来通り `parseMarkdown` が `FrontmatterParseError` を投げる）。
   - `src/sync/diff.ts`: `resolveArticleTarget()` 内のフォールバック ID 抽出（L74）で `parseMarkdownLenient(content, fullPath)` を使用する。
2. **[src/cli/commands/status.ts](file:///Volumes/ext/github/emdash-emit/src/cli/commands/status.ts) の `reportActionFailure` ラップ**:
   - `emit status`、`emit diff`、`emit init` の各 `.action(...)` を `try { ... } catch (err) { reportActionFailure(err); }` でラップし、`emit status --profile nonexistent` 等で生スタックトレースが出ないことを保証する。

## 3. ステップ B: `.agents/skills/` への `pstack` 流 3 大スキル導入

Antigravity の Workspace Customizations 自動検出仕様（`.agents/skills/<name>/SKILL.md`）および Claude Code / Cursor からも参照可能な標準 Markdown Skill 形式で、Emit 専用にチューニングした 3 つの品質管理スキルをリポジトリに同梱します。

```text
.agents/
└── skills/
    ├── interrogate/
    │   └── SKILL.md   # 実行証明必須の敵対的コード／計画書レビュー
    ├── correct/
    │   └── SKILL.md   # ミスの構造化（Arch → Type → Axis/Guard → Test → Doc）
    └── blast-radius/
        └── SKILL.md   # Layer 0/1・Schema 変更時の波及範囲と安全根拠の実証
```

### 3.1 `.agents/skills/interrogate/SKILL.md`（実行証明付きの敵対的レビュー）

- **用途**: 未コミット差分、ブランチ差分、または `docs/plans/v0.1.0XX-*.md` の実装計画書に対する敵対的レビュー（「この変更・計画をレビューして」「穴を探して」「interrogate して」）。
- **Emit 特化のルール**:
  1. **Run-Proven Survival Rule（実行証明なき指摘の自動破棄）**:
     - コード差分のレビューでは、各指摘に **「実行した再現コマンド（`npx vitest run ...` または `node --input-type=module -e ...`）とその実際の出力」** を添付しなければならない。
     - 計画書のレビューでは、各指摘に **「実コードに対する検証コマンド（`grep -n`, `tsc`, または既存関数のシグネチャ・テーブル定義の実測出力）」** を添付しなければならない。
     - 実行せずに書いた推測（「〜かもしれない」「将来〜すると危ない」）・スタイル指摘・すでに別レイヤでガードされている誤認は **本編から除外（Drop）** し、末尾に `Dropped findings: <N> (unproven / speculative)` として件数と1行理由のみ記載する。
  2. **Emit 7 大不変条件チェックリスト**:
     - レビュアーが必ず検証する攻撃ベクトルとして、Two-Track Revision、Two-Layer Representation、Two Media ID Spaces、Draft Selective Single GET（`body_source` / `taxonomy_verified`）、Epistemic Search（`walkComplete`）、4-Tier Layering（Axes 0–9）を内蔵する。

### 3.2 `.agents/skills/correct/SKILL.md`（再発防止の構造エンコーダ）

- **用途**: バグ発見時、レビュー指摘修正時、またはユーザーが AI エージェントの行動を訂正したとき（「二度と起きないようにして」「correct して」）。
- **Emit 特化のルール**:
  1. **5 段階の強制力ヒエラルキー（上から順に検討し、上位で防げるなら下位だけで済ませない）**:
     - **Level 1: Architecture** — 不正な呼び出し自体を隠蔽し、単一のエントリポイント（例: `commitArticleSnapshot`, `parseMarkdownLenient`）に集約する。
     - **Level 2: Types** — Branded Types（`MediaRecordId`, `StorageKey`）や Discriminated Union で不正状態を型エラーにする。
     - **Level 3: Structural Gate (`tests/layering.test.ts` / `tests/guards.test.ts`)** — 型で防げない呼び出し規約やレイヤ違反を Axis 検査として追加し、エラー文に「代わりに使うべき関数名とファイルパス」を含める。
     - **Level 4: Behavior Test (`tests/*.test.ts`)** — 内部実装ではなく、CLI / MCP / SQLite の観測可能な振る舞いを検証するテストを書く。
     - **Level 5: Docs (`AGENTS.md` / `docs/*.md`)** — 判断基準のみを書き、`AGENTS.md` §3 の **Rule ⇔ Enforcer 表** を更新する。
  2. **Fail-First Proof**: 新しいゲートやテストが「修正前のコード（または意図的に壊した状態）で確実に Fail すること」を実行して確認してから修正を適用する。

### 3.3 `.agents/skills/blast-radius/SKILL.md`（波及範囲と安全根拠の実証）

- **用途**: Layer 0（`src/db/`, `src/client/`, `src/utils/`）、Layer 1（`src/sync/taxonomies.ts`, `baseline-reconstruction.ts`, `preflight.ts`, `guards.ts`）、または `cache.db` スキーマを変更する前後の影響検証。
- **Emit 特化のルール**:
  1. **"The One Fact It's Safe Because Of"（安全性を支える核心の事実）の特定と Level 4 実証**:
     - 単に `grep` で呼び出し元を列挙するのではなく、「なぜこの変更が既存の `sync_state.local_hash` や `base_snapshots`、MCP JSON-RPC 出力を壊さないのか」という核心の事実を 1〜2 個特定し、実コードを呼び出すテスト／スクリプト（Level 4: _You ran it_）で証明する。
  2. **grep では見えない Emit の暗黙境界チェック**:
     - ① SQLite カラムとマイグレーション（v1〜v6 からのアップグレード時に既存 `local_hash` が無効化されないか — `tests/migration_hash_invariants.test.ts`）
     - ② Layer A（`base_snapshots` の `%e6%9c%aa%e5%88%86%e9%a1%9e` / `/_emdash/api/media/file/...`）と Layer B（ディスク上の `未分類` / `../../media/...`）の往復整合性
     - ③ CLI と MCP の出力対称性（`src/presentation/` と `_meta` / `isError: true`）
