## 1. 背景と目的

v0.1.12 から v0.1.45 までの 30 回以上にわたる迅速な機能改善・リファクタリングにより、コードベース（`src/` 118 モジュール、テスト 72 ファイル / 892 tests 全 green）は 4 層アーキテクチャと自動品質ゲート（`tests/layering.test.ts`, `tests/guards.test.ts`）によって極めて高い整合性を保っている。

一方で、各バージョンの改修仕様や不変条件（Invariant）をその都度 `README.md`、`AGENTS.md`、および `docs/v01xx-*` に追記してきた結果、ドキュメント体系に以下の課題が生じている：

1. **`README.md` の肥大化（1,322 行 / 約 80KB）**:
   - リポジトリの「看板（導入・コンセプト・基本操作）」と「全 CLI/MCP オプションの完全リファレンス」と「内部 SQLite スキーマ・エッジケース仕様」が 1 ファイルに混在しており、人間にとって通読困難な状態になっている。
2. **`AGENTS.md` の実装ノート堆積（359 行 / 約 52KB）**:
   - 「記事執筆 AI エージェント向けの運用ルール」と「Emit 開発者/AI 向けのアーキテクチャ憲法」が混在し、後半には過去のバグ経緯や関数・行番号単位の細かな実装ノートが 1 段落数千文字の箇条書きとして蓄積している。
3. **`docs/` 直下の計画書乱立とソート崩れ（移動対象 36 アイテム：計画書フォルダ 33 個 + バックログ 2 ファイル + 過去設計書 1 ファイル ＋ 本計画書 1 ファイル = 計 37 アイテム）**:
   - `docs/` 直下に `v0112-eval` 〜 `v0145-refactor-plan` が並び、何の計画書か名前から判別できない。
   - 中身が `README.md` 1 ファイルのみのフォルダが 28 個あり、エディタで開くとすべて `README.md` タブになって識別しづらい（複数ファイルを持つフォルダは `v0112`, `v0113`, `v0114`, `v0116`, `v0131` の 5 個）。
   - 現在のシステム仕様を示す「境界（ドメイン）ごとの詳細設計書」が `media-id-spaces.md` 以外に存在せず、最新の全体仕様を把握するには `AGENTS.md` と過去の計画書を横断して読む必要がある。

### 本計画のゴール

1. **過去計画書・バックログの `docs/plans/` への集約と案 A（SemVer ゼロ埋め + トピック名 + 単一ファイルフラット化）による再命名**
2. **`docs/` 直下への「プログラム境界ごとの詳細設計書（正典 Specifications）」の新設**
3. **`AGENTS.md` の「アーキテクチャ憲法＋コア不変条件＋例外台帳ルール＋開発ガバナンス」へのスリム化（詳細仕様は `docs/` 正典へ移管・リンク）**
4. **`README.md` の「看板（導入・コンセプト・クイックスタート・コマンド概要一覧）」への再構成（全 13 H2 セクションを情報欠落ゼロで `docs/` へ移管・再配置）**

## 9. 詳細設計 5（Rev.3 追加）: Emit の独自機能アピール強化と ASCII アーキテクチャ図の導入（提案 A・B・C）

### 9.1 背景と設計方針（なぜ Mermaid ではなく ASCII ダイアグラムか）

1. **独自機能の訴求不足の解消**:
   - Emit には一般的なヘッドレス CMS 同期ツールにはない高度な独自機能（特に **Portable Text ⇔ Markdown のロスレス双方向変換**、**二層表現によるオフライン画像プレビューと日本語デコード表示**、**公開記事の未公開ドラフト `published*` 共存**、**構造認識型ハイブリッド 3-Way Merge**、**AI の暴走・ハルシネーションを物理阻止する G1〜G19 ガードと認識論的検索**）が備わっている。
   - しかし従来の `README.md` ではフラットな箇条書きの 1 行に埋もれていたため、初見の開発者や AI ユーザーにその技術的価値が伝わりにくかった。
2. **レンダラー非依存（npm / GitHub / エディタ生テキスト / AI コンテキスト完全互換）**:
   - `README.md` は `package.json` の `"files"` に同梱され **npmjs.com のパッケージページに直接表示される**が、npmjs.com の Markdown レンダラーは Mermaid（```` ```mermaid ````）をレンダリングできず生のコード文字列として露出してしまう。
   - また、`docs/*.md` をエディタで生テキストとして読む開発者や、テキストトークンとして読み込む AI エージェントにとっても、罫線文字（`┌─┐`, `│`, `◄──►`）で描かれた **ASCII アーキテクチャ図**の方がその場で視覚的・構造的に理解できる。
   - したがって、**`README.md` および `docs/*.md` のすべての図解を、既存のトーンに統一した高品質な ASCII ダイアグラムで記述する**。

### 9.2 【提案 A】`README.md` の `## 🌟 Key Features` を「4 大技術ピラー + ASCII 図解」へ強化

`README.md` の `## 🌟 Key Features` セクションをフラットな箇条書きから、Emit の独自性を前面に押し出した **4 つの技術ピラー（柱）** に再構成する（行数目安：全体で 350〜450 行以内に収め、看板としての読みやすさを維持）：

1. **Pillar 1: Lossless Portable Text ⇔ Markdown Bidirectional Sync (3-Tier AST Engine)**
   - EmDash 固有の Portable Text JSON AST と標準 Markdown の双方向ロスレス往復をアピール。
   - **3-Tier 変換と Dual-Track Image の ASCII ミニ図解**を掲載：
     - **Tier 1 / 2 (Standard & GFM)**: 見出し、リスト、インライン装飾、GFM テーブル（`| col |`）、水平線（`---`）、および装飾なし標準画像（**Track A**: `![alt](../../media/<storageKey>)` ※ローカルミラー `media/<markdownRef>.<ext>`、通常の `storageKey` は `<ulid>.<ext>` のため一致）はクリーンなネイティブ Markdown に変換。
     - **Tier 3 (Opaque Block Preservation)**: Web 管理画面で設定された画像のレイアウト属性（`alignment: left/center/right`, `displayWidth`, `caption`）やカスタムブロック（`core:gallery` 等）は、標準 Markdown 変換で属性が抜け落ちて `push` 時にサーバー側のスタイルが先祖返り（破壊的リセット）するのを防ぐため、1 行の不透明コメントフェンス（**Track B**: `<!--ec:block {"_type":"image",...} -->`）に自動カプセル化し、Preflight Guard **G9 (`MODIFIED_OPAQUE_BLOCK`)** で保護する。
2. **Pillar 2: True Local-First Offline Authoring & Two-Layer Representation (Layer A ⇔ Layer B)**
   - **オフライン画像プレビュー (`localMediaRefs: true`)**: ベースラインとリモート通信（Layer A）は正規 URL `/_emdash/api/media/file/<storageKey>` を保ったまま、ローカルディスク（Layer B）は記事からの相対パス `../../media/<storageKey>`（＝ローカルミラー `media/<markdownRef>.<ext>`）で表記するため、オフラインの飛行機内でも VS Code / Cursor / Obsidian のプレビューで画像がそのまま表示され、かつ `emit diff` で Phantom Diff が一切出ない。
   - **新規下書き画像の全自動昇格 (`media/drafts/`)**: ローカル画像を `media/drafts/` に置いて Markdown から参照して `emit push` するだけで、4 段階アップロード・正規 URL 書き換え・`media/<markdownRef>.<ext>`（＋ `.yaml`）への移動（昇格）・複数記事間での重複アップロード防止まで全自動で完結する。
   - **日本語タクソノミーのデコード表示**: サーバー側の `%e6%9c%aa%e5%88%86%e9%a1%9e`（Layer A）を、ローカル Frontmatter や YAML では人間と AI がそのまま読める `未分類`（Layer B）として扱う。
3. **Pillar 3: CMS-Grade Concurrency, Two-Track Revisions & Structure-Aware 3-Way Merge**
   - **公開記事の未公開ドラフト共存 (`published*`)**: Web 管理画面で「公開中の記事を下書き保存」した状態を、Transport 用リビジョン（Track 1）と比較用複合キー `${version}@draft:${draftRevisionId}`（Track 2）の分離により完全追従。ローカルではファイルを移動させず `status: published # draft revision` (`published*`) として可視化し、通常 `push` でドラフト更新、`--allow-publish` で本番反映できる。
   - **構造認識型ハイブリッド 3-Way Merge & 分散ロック**: 7 分間の分散ミューテックスリース（`POST /lock`）に加え、競合時はファイルを単なるテキストとしてマージするのではなく、**① Frontmatter はキー単位、② Categories/Tags は集合（Set）単位（Pre-PUT Remote Taxonomy Audit 付き）、③ 本文は `node-diff3` で行単位**に独立マージし、ローカル変更は `posts/conflicts/` へ安全に保護する。
4. **Pillar 4: Hardened for Autonomous AI Agents (19 Guardrails & Epistemic Search)**
   - **19 のコードレベル安全ガード (G1–G19)**: AI の誤操作（未承認の本番公開 G3、存在しないタグの捏造 G4、`mv` によるファイル名破壊 G2、隔離ファイルの誤プッシュ G12、タクソノミー全消去 G19 等）をネットワーク通信前に物理的に阻止。
   - **Epistemic Search (`[WALK_INCOMPLETE]`) & 0-GET 自己修復**: `article-search` / `media-search` が走査上限で停止した際は `[WALK_INCOMPLETE]` を明示し、AI が「リモートに記事が存在しない」と誤断定（ハルシネーション）することを防ぐ。またリモートで削除されたタグの除去や古い表記の修復を 0-GET Fast-path で自動実行する。

### 9.5 【提案 D】執筆ワークフロー図（The Golden Path）の実運用フローへの進化（Workflow A/B 分岐 ＋ 2-Stage Push）

初版から引き継がれていた単一 1 本道の「4-Step Authoring Cycle（Pull → New/Status → Edit → Push）」を、v0.1.20〜v0.1.45 で確立された実際の運用フローに即して以下のように進化させる（`README.md` および `AGENTS.md` §4 を同期更新）：

1. **入り口の 2 分岐化（Workflow A vs Workflow B）**:
   - **Workflow A（新規記事の One-Shot 起案）**: `emit pull` で最新のタクソノミー定義を同期した上で、`emit new <slug> -t ... -C ... -T ... -d ... -f ...`（MCP `sync_new`）により **YAML フロントマターを手編集することなく 1 ステップで完全な下書きを生成**する（v0.1.20 仕様）。
   - **Workflow B（既存・過去記事の検索＆ピンポイント改訂）**: スライディングウィンドウ（直近 30+30 件）内の記事は `emit status` で確認し、ウィンドウ外の過去記事は `emit article-search`（キーワード・タグ・カテゴリ・日付範囲・`--offline` 本文検索）で 26 文字 ULID を特定してから `emit pull <ULID>` でオンデマンドに作業机（Staging Desk）へ引き出す（v0.1.43 / v0.1.44 仕様）。
2. **オフライン執筆＆メディア連携の明示**:
   - 新規ローカル画像は `media/drafts/<file>` に配置、スマホや Web から先行アップロード済みのリモート画像は `emit media-search`（`--since`, `--offline`）で探索（v0.1.29 / v0.1.42 仕様）、`<!--ec:block ... -->` は G9 で保護（v0.1.35 / v0.1.36 仕様）。
3. **出口の 2 段階 Push（Draft Staging ──► Live Publish）の明示**:
   - **Stage 1（Draft Staging: `emit push <file>`）**: 下書き保存に加え、**すでに本番公開中（`status: published`）の記事であっても、`--allow-publish` なしの素の `emit push` によって本番（Live）を書き換えずにリモートへ未公開ドラフトリビジョン（`published*` / `status: published # draft revision`）として安全にステージング保存できる**ことを明記（v0.1.24 / v0.1.41 仕様）。
   - **Stage 2（Live Publish: `emit push <file> --allow-publish`）**: 推敲完了後に本番 Web へ反映する。
