# v0.2.0 追加実装計画書 (Part 2): カスタムスキーマ対応（非破壊パススルー ＋ シンプル型 `fields:` 編集）

- **対象バージョン**: `v0.2.0`（未プッシュの `v0.2.0` コミットへ統合）
- **作成日**: 2026-11-27
- **ステータス**: **実装済み（2026-11-27、`v0.2.0` 統合）**
- **前提**:
  - 通常のブログ記事（`posts` かつカスタムフィールドなし）に対しては **ディスク出力 100% バイト不変** を維持する。
  - フロントマターの肥大化・記述ミスを防ぐため、**「編集する対象（シンプル型）」と「壊さず温存する対象（複雑型）」を明確に分離**する。

---

## 1. 課題と設計方針

### 1.1 現状の課題（`v0.2.0` 時点）

- `apiResponseToLocal()`（`src/client/mapper.ts`）は `item.data` から `title`, `content` / `body`, `featured_image` のみを抽出し、他のカスタムフィールドを破棄している。
- `localToApiPayload()`（`src/client/mapper.ts`）は `{ title, content, featured_image? }` のみで `payload.data` を組み立てるため、カスタムフィールドを持つ記事を `pull` → `push` すると、**サーバー側のカスタムフィールド値が欠落（または必須チェックで HTTP 400）するリスク**がある。

### 1.2 基本方針（2 層分離アーキテクチャ）

1. **非破壊パススルー（Opaque Preservation — DB 側保持）**:
   - フロントマターを散らかす原因になる **複雑型カスタムフィールド**（ネストしたオブジェクト、複数リッチテキスト配列、オブジェクト配列など）は Markdown フロントマターに出力せず、SQLite キャッシュ（`base_snapshots.extra_data_json`）にそのまま JSON 保持し、`push` 時の `payload.data` へ非破壊マージして返却する。
2. **シンプル型フィールドの YAML 編集（Frontmatter `fields:`）**:
   - 人間・AI エージェントが安全かつ直感的に編集できる **シンプル型**（`string`, `number`, `boolean`, `null`, `string[]`）のみを、フロントマターの予約名前空間 `fields:` にシリアライズして編集可能にする。
   - `fields` が空（0 キー）の既存 `posts` 記事では `fields:` ブロック自体を出力しない。
3. **明確な非スコープ（管理画面・EmDash MCP に委譲）**:
   - 1 記事内の複数リッチテキスト（Portable Text）フィールドのローカル Markdown 編集（非破壊パススルーによる温存のみ行う）。
   - 深いネスト構造・UI レイアウトビルダー用 JSON の YAML 編集。
   - コレクション／フィールドスキーマ定義自体の作成・変更（`schema_create_field` 等）。

### 1.3 着手前確認事項（一次情報ゲート）

- **確認結果（2026-11-27 記録）**:
  - EmDash REST API `PUT /_emdash/api/content/{collection}/{id}` は `{ data: { ... }, _rev }` 形式で `data` オブジェクトを受け取り、ドラフトリビジョンへ保存する。バージョンや更新経路（通常 PUT vs ドラフトマージ）により置換・部分マージの双方の挙動があり得るため、Emit 側は以下の**両立契約**を採用する：
    1. `push` 時は `base_snapshots.extra_data_json` の `opaqueExtraData` を毎回フル復元して `payload.data` に含める（置換意味論でも複雑フィールドを 100% 温存）。
    2. `fields:` の明示的な値クリア・削除は `fields.<key>: null` 送信をサポートする（部分マージ意味論でも確実に削除を反映可能）。
  - カスタムコレクションの本文フィールドは Phase 1 では `content` / `body` 優先とし、本文フィールドを持たないコレクションは `body = ''` ＋ `fields` / `extra_data_json` で往復させる。

## 2. 機能別設計

### Feature 1: SQLite Schema v9 — `base_snapshots.extra_data_json`（Layer 0）

- **`src/db/migrations.ts`**:
  - `CURRENT_CACHE_SCHEMA_VERSION` を `8` → `9` に更新。
  - `base_snapshots` テーブルに `extra_data_json TEXT`（Nullable）を追加する加算的マイグレーション（`ALTER TABLE base_snapshots ADD COLUMN extra_data_json TEXT`）を実装。
- **`src/db/cache.ts`**:
  - `BaseSnapshot` 型および `saveBaseSnapshot()` / `getBaseSnapshot()` に `extraDataJson?: string | null` を追加。
  - 既存の `extraDataJson` が `null` / `undefined` のレコードは従来と同一挙動。

### Feature 2: Frontmatter `fields:` スキーマ＆決定論的シリアライズ（Layer 0）

- **`src/utils/frontmatter.ts`**:
  - シンプル型スキーマを定義：
    ```ts
    export const CustomFieldScalarSchema = z.union([
      z.string(),
      z.number(),
      z.boolean(),
      z.null(),
      z.array(z.string()),
    ]);
    ```
  - `FrontmatterSchema` に `fields: z.record(CustomFieldScalarSchema).optional()` を追加。
  - `formatFrontmatterYaml()` にて、`data.fields` に 1 つ以上キーがある場合のみ `fields:` ブロックをキー昇順（`Object.keys(data.fields).sort()`）で決定論的に出力：
    - `string` → `formatYamlScalar(val)`
    - `number` / `boolean` → リテラル出力
    - `null` → `null`
    - `string[]` → 空なら `[]`、要素があれば `    - ${formatYamlScalar(v)}`
  - `data.fields` が `undefined` または空オブジェクト `{}` の場合は出力しない（既存 `posts` 記事のバイト完全不変を保証）。

### Feature 3: Mapper の 2 層分類と非破壊マージ（Layer 0）

- **`src/client/mapper.ts`**:
  - 予約済み `data` キー定数: `RESERVED_DATA_KEYS = new Set(['title', 'content', 'body', 'featured_image', 'featuredImage'])`。
  - **`apiResponseToLocal()`**:
    - `item.data` の各キーを走査し、`RESERVED_DATA_KEYS` 以外を以下のように分類する：
      - `isSimpleCustomFieldValue(val)` が `true`（`string | number | boolean | null | string[]`）→ `fields[key] = val`
      - それ以外（ネストしたオブジェクト、Portable Text 配列、オブジェクト配列など）→ `opaqueExtraData[key] = val`
    - 戻り値に `opaqueExtraData?: Record<string, unknown>` を追加（空なら省略）。
  - **`localToApiPayload()`**:
    - `MapperOptions` に `opaqueExtraData?: Record<string, unknown>` を追加。
    - `payload.data` を以下の優先順位で構築する：
      1. `...(options?.opaqueExtraData ?? {})`（複雑フィールドを非破壊復元）
      2. `...(frontmatter.fields ?? {})`（ローカルで編集されたシンプル型フィールドを反映）
      3. `title: frontmatter.title`, `content: ptBody`, `featured_image`（予約フィールドを最後に確定）
    - 予約キー（`title`, `content`, `body`, `featured_image`, `featuredImage`）と同名のキーが `frontmatter.fields` に指定された場合は暗黙無視せず、Preflight 段の **Guard G24 (`RESERVED_CUSTOM_FIELD_KEY`)** として **エラー拒否** に固定する（`src/sync/guards.ts` の `GUARD_REGISTRY` に登録）。

### Feature 4: Pull / Push / Commit / Merge 経路の連結（Layer 1–2）

- **3-Way Merge の leaf 粒度化（Layer 1: `src/sync/merge.ts`）**:
  - `mergeFrontmatter()` に `key === 'fields'` 専用分岐（`mergeCustomFields()`）を追加し、`fields` オブジェクト全体ではなく **`fields.<key>`（leaf キー）単位** で 3-Way マージを行う。
  - これにより「リモートが `fields.a` を更新し、ローカルが `fields.b` を編集した」ケースで両方の変更が安全に保持される（同一 leaf キーの真の衝突時のみ既存ルール通り remote 優先＋警告）。
- **Pull 経路**（`src/sync/pull/index.ts`, `src/sync/pull/fast_path.ts`, `src/sync/workspace/commit.ts`）:
  - `apiResponseToLocal()` が返した `opaqueExtraData` を `commitArticleSnapshot()` 経由で `base_snapshots.extra_data_json` に保存（空なら `null`）。
- **Push 経路**（`src/sync/push/index.ts`, `src/sync/push/merge_stage.ts`, `src/sync/push/commit.ts`）:
  - `base_snapshots` から `extraDataJson` を読み出し、`JSON.parse` して `localToApiPayload(..., { opaqueExtraData })` へ渡す。
  - 3-Way Merge 発生時（`merge_stage.ts`）は、リモート最新の `opaqueExtraData` を優先して保持しつつ、ローカルの `fields.<key>` 変更を leaf 粒度でマージする。
  - `push` 後のサーバーレスポンスから最新の `opaqueExtraData` を再抽出し、`base_snapshots.extra_data_json` を更新する。
- **Diagnostics / Visibility**（`src/sync/status.ts`, `src/sync/diff.ts`, Layer 3 出力）:
  - `fields:` の変更は通常のフロントマター差分として `emit status` / `emit diff` で自動的に検知・表示される。
  - `opaqueExtraData` が存在する記事を `pull` した際の情報通知（`Preserved N complex custom field(s) in cache (opaque pass-through).`）は **Axis 5 に従い Layer 2 から直接 `console.log` せず**、`PullResult.warnings`（または戻り値フィールド）経由で Layer 3（CLI / MCP）に出力する。
