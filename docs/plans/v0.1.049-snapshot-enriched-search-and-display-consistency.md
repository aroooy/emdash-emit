# v0.1.49 計画書: スナップショットによる FTS ヒット補完と検索/診断表示の一貫性（エンドユーザー要望 P0–P3）

- **対象バージョン**: `v0.1.49`
- **作成日**: 2026-11-22
- **ステータス**: **レビュー待ち（Draft）** — ライブ API 待ちの Phase 0 実測ゲートは**不要**（全項目が v0.1.48 コードの `file:line` 実測に基づく局所改善。§3.1 の rev 検証分岐は FTS 応答に `_rev` が無い現状実測を前提に確定済みで、ユニットテストのみで完結）。プロジェクトオーナーの承認後に実装着手。
- **起点**: エンドユーザーからの 4 件の UX フィードバック（リモート FTS 検索時の `---- [unknown]`、オフライン誘導ヒントの旧文言、`--limit` 打ち切りメッセージの不統一、doctor の Unreferenced Media に `.yaml` が代表例として出る違和感）。
- **目的**:
  1. **P0: FTS ヒットの snapshot Enrichment** — `GET /_emdash/api/search` は status / 日付を返さないため FTS hit が常に `---- [unknown]` になる。同じファイルに既に実装済みの `'snapshot-hit'` fast-path（rev 検証付き `snapshot_articles` 参照）と同じ論理で、FTS パスの hit にも date / status を補完する。**新規設計ではなく既存パターンの適用漏れ補完**。
  2. **P1: オフライン誘導ヒントの snapshot 対応** — v0.1.47 で `--offline` は全ライブラリスナップショットを検索できるようになったが、ヒント文言は「workspace-synced articles」のまま。件数・取得日時・鮮度を添えて新機能の発見性を上げる（stale 明示を必須条件とする）。
  3. **P2: article-search の hit-limit 補足行** — メディア検索（v0.1.44 の `formatMediaSearchHitLimitNotice()`）にある「Hit limit reached at N; raise --limit ...」補足行が、記事検索の scan path に未搭載。FTS パスは hit-limit で `walkComplete: false` にすらならないため、打ち切り理由の表示も揃える。
  4. **P3: doctor `media_isolated` の表示ラベル整合** — metadata-only（companion YAML のみ・バイナリ無し）アセットが「local media file(s)」の代表例として `.yaml` を見せる違和感を解消する。**削除挙動は一切変更しない**。

## 3. 詳細設計仕様

### 3.1 P0: FTS ヒットの snapshot Enrichment（`src/sync/article_search/remote.ts`）

#### 原則

FTS 経路は hit の `id`（26 文字 ULID）を確実に持つ。`snapshot_articles` は PK が `id` なので O(1) lookup で、rev 検証済みの Layer A メタデータ（status / created_at / published_at / updated_at）を引っ張れる。判定条件は scan path の `'snapshot-hit'` fast-path（`remote.ts:276-293`）と**同一の語彙・同一の rev ルール**を使い、新規ヘルパーを作らない。

#### 補完ルール（FTS hit ループ内に追加）

各 FTS hit について `options.cache?.getSnapshotArticle(item.id)` を読む:

| 条件 | 動作 | hit フラグ |
| --- | --- | --- |
| snapshot 行なし | 従来どおり（`---- [unknown]`）。**何も補完しない・何も断定しない** | なし |
| 行あり **かつ** FTS 応答に rev 候補（`item._rev` / `item.version`）があり `isSameRev(snap.comparisonRev, extractRev(item))` が真 | `status` / `createdAt` / `publishedAt` / `updatedAt` を snapshot から補完（**検証済み**） | `enrichedFromSnapshot: true` |
| 行あり **だが** FTS 応答に rev 候補が無い、または rev 不一致 | 同じく補完するが、値がスナップショット時点のものであることを明示 | `enrichedFromSnapshot: true` + `enrichmentStale: true` |

- **rev 検証分岐は現状実測で確定済み（Phase 0 ゲート不要）**: v0.1.48 の `RawSearchItem`（`remote.ts:55-63`）に `_rev` / `version` は存在せず、EmDash search API は status・日付と同様に rev も返さない（v0.1.43 Phase 0 実測）。よって**基本経路は `enrichmentStale: true` 付き補完（表示 `[enriched: snapshot (unverified)]`）**であり、rev 候補が将来 API に追加された場合のみ `isSameRev()` による検証済み昇格が発火する。分岐自体は `RawSearchItem` にオプショナル rev フィールドを追加して両経路をユニットテストで固定するため、ライブ環境待ちのゲートは不要。
- `body_markdown` は**読まない・使わない**（メタデータのみ）。`list-stale` 行でも date / status の鮮度は taxonomy/body と独立に信頼できるが、上記 rev ラベルは body_source によらず一律で付与する（過信防止）。
- **FTS に slug フィルタがある場合（`remote.ts:152-159`）**: snapshot の `slug` で補完判定を拡張しない（挙動変更を避ける。本版は表示強化のみ）。
- **後方互換（`result.snapshot` 付与）**: リモート検索に `ArticleSearchSnapshotInfo` を載せるのは `getSnapshotMeta(collection)` が行を返したときだけとし、`local.ts:370` と同一の spreading を使う — `...(snapshotInfo ? { snapshot: snapshotInfo } : {})`。`snapshot: undefined` キーを載せないことで、既存テストの `toEqual` と MCP JSON 出力への影響をゼロに保つ。

#### 型追加（Layer 2、追加のみ後方互換）

```ts
// src/sync/article_search/types.ts — ArticleSearchHit に追加
/** True when date/status were filled from the local snapshot catalog (FTS returns neither). */
enrichedFromSnapshot?: boolean;
/** True when enrichment could not be rev-verified against the live remote revision. */
enrichmentStale?: boolean;

// src/sync/article_search/types.ts — ArticleSearchResult に追加（scan path でも設定可）
snapshotEnrichedCount?: number; // 補完できた hit 数
```

`ArticleSearchResult.snapshot?: ArticleSearchSnapshotInfo` は**リモート検索でも設定する**（`getSnapshotMeta(collection)` から `capturedAt(ISO) / ageDays / stale / articleCount` を構築。`local.ts:248-256, 370` の既存構築ロジックを再利用し、行が無いときはキー自体を載せない）。これにより P1 のヒント文言が同じ info を消費できる。MCP payload には既に offline 時のみ framing が乗るため、remote 時は `snapshot` フィールドをそのまま payload に追加する。

rev 検証入力のため `remote.ts` の `RawSearchItem` にオプショナルフィールド `_rev?: string; version?: string;` を追加する（読み取り専用の型緩めであり、現行 API 応答では undefined のまま。rev 抽出は Layer 0 既存の `extractRev()` / `extractComparisonRev()`（`src/client/api.ts`）を使い、rev 比較は scan path と同じ `isSameRev()` を適用する）。

#### 表示（Layer 3、`formatArticleSearchHit()`）

基本経路（現状の FTS は rev を返さない）は `2023-03-09 [published] ... [remote only] [enriched: snapshot (unverified)]`。rev 候補が将来 API に載り検証が通った場合のみ `[enriched: snapshot]`（`(unverified)` なし）。スナップショット無し hit は現状出力のまま（バイト一致）。語彙は既存の `[snapshot]` / `[body unverified]`（v0.1.47）と整合させるが、offline 検索の `[snapshot]`（行そのものが snapshot 由来）とは意味が違うため新ラベルを立てる。

#### レイヤリング

- `remote.ts`（Layer 2）→ `cache.getSnapshotArticle()` / `getSnapshotMeta()` は Layer 0 の既存メソッド、`isSameRev` は Layer 0 の既存 import（`remote.ts:27`）。**新規 import edge なし**。
- Layer 2 sibling 結合追加なし、`ALLOWED_LAYER_2_SYMBOLS` 変更なし（`ArticleSearchHit` / `ArticleSearchResult` は既に許可済みで、フィールド追加は型内部 → gate 対象外。v0.1.44 §3.2 と同じ扱い）。


### 3.3 P2: article-search の hit-limit 補足行（presentation + CLI + MCP）

#### 対象の是正（要望3の実態）

- **FTS パスは変更しない**（`walkComplete = !nextCursor` が正しく「次カーソル残存＝追加結果あり」を表現済み。`truncated: true` は payload とヘッダー `[truncated at limit]`（`article_report.ts:306`）に出ている）。
- 修正するのは **scan path の `[WALK_INCOMPLETE]` 通知**と、その MCP ハードコード note の 2 箇所。

#### 設計

`formatArticleSearchWalkIncompleteNotice(result, options?: { limit?: number; isMcp?: boolean })` にシグネチャ拡張（オプショナル引数 = 後方互換）で、media-search と同一の判定・語彙を導入する:

```ts
const hitLimitLine =
  result.truncated && result.hits.length >= (options?.limit ?? 20)
    ? `Hit limit reached at ${result.hits.length}; raise ${isMcp ? 'limit' : '--limit'} to see more matches from the same walk.`
    : null;
```

- CLI（`src/cli/commands/article-search.ts:118`）は `clampSearchLimit(options.limit)` の結果を渡す。
- MCP（`sync-article-search.ts:120-122`）のハードコード note を、**同一 presentation 関数 + `{ isMcp: true }` オプション**経由に置換し、`maxScan` / `--limit` の語彙分岐を `formatMediaSearchWalkIncompleteNotice()`（`media_report.ts:131-150`）と揃える。これで対称性テスト（`tests/presentation_symmetry.test.ts`）の守備範囲に入る。
- 語彙は media-search と**一字一句同一**にする（`Hit limit reached at N; raise --limit to see more matches from the same walk.`）。文案の重複を防ぐため、**本版の同じ変更内で** `article_report.ts` に共有ヘルパー `formatSearchHitLimitNotice(hitCount, options?: { isMcp?: boolean })` を新設し、`media_report.ts` の `formatMediaSearchHitLimitNotice()`（L120-126）をそこから呼ぶ薄いラッパーへ置き換える。`media_report.ts` は既に `article_report.ts` を import 済み（`media_report.ts:23-27`）で、**新規 Layer 3 内 import edge は増えない**。既存の media 側呼び出し側（`src/cli/commands/media.ts`、`src/mcp/tools/sync-media-search.ts`）とテスト `tests/media_search.test.ts:1450-1457` は `formatMediaSearchHitLimitNotice()` の公開シグネチャ・文案不変で無変更通過。
- **エラーコード追加なし・`--limit` / `--max-scan` の撤廃なし**（v0.1.44 §3.1 と同じ方針: 両者は別軸のノブ）。

### 3.4 P3: doctor `media_isolated` のラベル整合（`src/sync/doctor.ts`）

#### スコープ（要望4は狭めて採用）

バイナリ優先表示（`comp.binaryFile || comp.yamlPath`）は**実装済み**なので変更しない。やることは 2 点だけ:

1. `isolatedMedia` の分類を message に反映: metadata-only（`binaryFile == null`）の件数を数え、**全件が metadata-only のときだけ**文案を
   `${n} media metadata entr(y/ies) (YAML companion only, no mirrored binary file) in media/ (...) are not referenced ...` にする。混在時は現行の `local media file(s)` を維持しつつ、代表例リストは **binary 有りのアセットを先頭**に並べる（表示順序のみ）。
2. `details.unreferenced[]` の各要素に `hasBinary: boolean` を追加（JSON details の追加フィールドであり MCP 互換）。

- `LocalCompanionAsset` に `hasBinary` は存在しないので、`isolatedMedia.push()` 時点で `binaryFile != null` から導出する。
- **削除・prune 提案は出さない**（剪定権限はリモートレコードのみ、AGENTS.md Invariant 3 / `docs/media-pipeline.md`）。`status: 'ok'` と overallStatus 不変も維持（v0.1.41 T3-3 の不変条件）。

## 9. リスクと却下した代替案

| 案 | 判定 | 理由 |
| --- | --- | --- |
| FTS hit ごとに `GET /posts/{id}` を発行して live 値を取得 | **却下** | N+1 HTTP。snapshot が無い場合は現状の `---- [unknown]` が誠実な表示であり、認識論上も正しい（「不明」を「不明」として出す） |
| snapshot rev 検証なしで常に補完しラベルも付けない | **却下** | Invariant 6 / epistemic rule に反する。編集済み記事の旧 status・旧日付を現在値として断言してしまう |
| FTS で hit-limit 到達時に `walkComplete: false` を立てる | **却下** | `nextCursor` の有無が打ち切り理由の真実であり、現状（`walkComplete = !nextCursor`）が正しい。要望3を額面どおり FTS 側へ適用すると誤った認識論変更になる |
| doctor で metadata-only アセットを「バイナリ欠損」warning に格上げ | **却下** | companion のみの残骸は informational という v0.1.40 方針および `status: 'ok'` 維持（v0.1.41 T3-3）と矛盾。健全ワークスペースを warnings に落とさない原則を守る |
| offline hint を「Full library can be searched」単文に統一 | **却下** | スナップショットは時点スナップショットであり live ライブラリではない。件数・日時・stale を添える表現に限る（§3.2） |
