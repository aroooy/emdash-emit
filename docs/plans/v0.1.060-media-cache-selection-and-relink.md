### 1.2 各指摘のユーザーペイン

- **①（4,000 枚規模の実運用）**：`emit snapshot --include-media` の既定予算は 200 件 / 512 MiB（`docs/media-pipeline.md:163`）。順序保証がないと、SQLite の物理走査順（INSERT / `INSERT OR REPLACE` の rowid 再利用履歴に依存）で先頭 200 件が選ばれ、「直近の記事で使う画像がキャッシュされず、オフライン執筆時に `[MEDIA_NOT_GUARANTEED]` になる」ことがありうる。ユーザーの推測（「物理配置順＝昔の登録順」）は厳密には必ずしも成立しないが、**「新しい画像が予算に入る保証がない」という帰結は正しい**。
- **②（手元整理後の復元不能）**：ディスク容量節約などで `media/` の実体を消した後オフラインになると、`emit pull --from-snapshot` が `[MEDIA_CACHE ... skipped=N]` と報告し、`media/_cache/` に実体が揃っていても再リンクしない。ミラー実体基準の診断（doctor `[MEDIA_CACHE_AVAILABLE]`、v0.1.59）とは**矛盾する挙動**でもあり、修正すれば両者が整合する。

### 1.3 スコープ方針（指摘案に対する本計画の改訂）

| #   | 要望原文                                                                               | 本計画での改訂                                                                                                                                   | 理由                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| --- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R1  | `ORDER BY created_at DESC` **または** `ORDER BY id DESC`（ULID 特性）で 200 件切り出し | **`ORDER BY created_at DESC` を採択**（`id DESC` は不採用）。加えて Stage 3b の候補構築側にも同じ順序を明示し、クエリ順序に単一障害点を置かない  | 実測（node:sqlite / Node v26.11）で、PRIMARY KEY 列 `media_id` への `ORDER BY media_id DESC` が B-tree 逆スキャン最適化により**ULID 辞書順と一致しない**（C collation の byte-order 比較とスキャナ短絡の相互作用）。`created_at` は ISO-8601 で辞書順＝時間順、既存インデックス `idx_snapshot_media_created_at`（`migrations.ts:232`）がそのまま使い消し可能、NULL（メタ欠損の移行レコード）は ASC 先頭＝DESC 末尾に回退して予算の後方へ回る。ULID 特性利用は Epistemic に安全でないため弃却 |
| R2  | 200 件切り出しを SQL 側（`LIMIT`）で行う                                               | **SQL には `LIMIT` を入れない**（全件 ORDER のまま）。予算切り出しは現行どおり Stage 3b の候補フィルタ後に行う                                   | スキップ条件（storageKey なし / ミラー済み / 既にキャッシュ済み）を通過した候補から先頭順に予算消費する設計では、SQL `LIMIT` を先に適用するとスキップされる 200 件で枠を浪費してしまう。件数千規模の ORDER BY はインデックス走査で十分高速であり懸念対象外                                                                                                                                                                                                                                   |
| R3  | ② の修正のみ言及                                                                       | `snapshot/index.ts:456` の **Stage 3b 側 `mirrorIndex.has()` も対称に `localPath` 判定へ変更**（キャッシュ取りこぼし防止）+ 候補の安定ソート追加 | Stage 3b は「ミラー済みなら再ダウンロード不要」の判定だが、`has()` のままでは②と同じ理屈で「実体は無いのに履歴だけある」キーがキャッシュ対象から永久に除外される。両箇所を同一基準（物理実体）で揃えないと invariant が半分にしか適用されない                                                                                                                                                                                                                                                |

## 2. 設計

### 2.1 DB 層: `listSnapshotMedia()` の newest-first 保証（`src/db/cache.ts:911`）

```ts
public listSnapshotMedia(): SnapshotMediaRecord[] {
  // Deterministic newest-first order. `created_at` is the server-assigned upload
  // time (ISO-8601, lexicographically sortable) and already carries
  // idx_snapshot_media_created_at; NULLs sort first in ASC, so DESC puts them last.
  // Budgeted Stage 3b cache downloads consume this list head-first, so the newest
  // assets win the mediaCacheLimit / mediaCacheMaxBytes budget on large libraries.
  const rows = this.db
    .prepare('SELECT * FROM snapshot_media ORDER BY created_at DESC')
    .all() as Array<Record<string, unknown>>;
  return rows.map((r) => this.mapSnapshotMediaRow(r));
}
```

- **呼び出し側 2 箇所への影響**:
  - `sync/snapshot/index.ts:444`（Stage 3b 候補構築）→ 予算消費順が newest-first になる（本変更の主目的）
  - `sync/media/local_search.ts:146`（snapshot マージ検索）→ limit トランケート時の残存件が新しい側に固定される。**副次効果として、ローカルメディア検索の snapshot-only ヒットが newest-first になり「recency browse」の表示品質が向上**する（`docs/cli-and-mcp-reference.md:281` の "browse newest media assets" 表現と整合）。
- **NULL `created_at` の扱い**: SQLite は NULL を ASC で最小に並べるため、DESC では末尾。メタ欠損レコード（移行時コーパス）は予算の最後方に回り、Epistemic に「不明＝新しい」と誤認しない。

### 2.2 Stage 3b: キャッシュ候補の newest-first 明示 & 物理実体基準スキップ（`src/sync/snapshot/index.ts:452-467`）

候補ループに 2 つの変更を入れる：

```ts
// (a) 物理実体基準のスキップ判定（② と同一 invariant、§2.3 と対称）
if (mirrorIndex.get(rec.storageKey)?.localPath) {
  mediaCacheSkipped++;
  continue;
}

// (b) 候補構築後・予算消費前に安定ソート（DB 順序への単一障害点を排除）
candidates.sort(
  (a, b) =>
    (b.rec.createdAt ?? '').localeCompare(a.rec.createdAt ?? '') ||
    b.rec.mediaId.localeCompare(a.rec.mediaId),
);
```

- (a) により、ミラー実体を誤削除したキーは次回 `snapshot --include-media` で `_cache/` の再取得候補に戻る（オンライン時しか修復できないが、② のオフライン復元と組み合わせることで最終的に自己修復される）。
- (b) は O(M log M)（M = 候補数）で、SQL 側の ORDER と同じ順序を宣言的に保証する。`created_at` NULL は `''` に正規化され末尾に回る。

### 2.3 展開層: `restoreSnapshotReferencedMedia()` の物理実体判定（`src/sync/pull/media_stage.ts:784-787`）

```ts
for (const storageKey of storageKeys) {
  // Only skip when the physical mirror binary actually exists on disk. A
  // `media_state` record alone (e.g. after the user accidentally deleted
  // `media/<file>` by hand) must not block re-materialization from cache.
  if (mirrorIndex.get(storageKey)?.localPath) {
    skipped++;
    continue;
  }
```

- **既存の自己防御はそのまま有効**: 展開ブロック内は既に `if (!fs.existsSync(mirrorAbsPath))`（`:834`）と companion `.yaml` の存在チェック（`:846`）、`saveMediaState()` の再実行で構成されており、判定を `localPath` に替えても上書き・重複書込みは発生しない。`media_state` は upsert で冪等。
- **companion YAML が残り binary のみ消えたケース**: companion は再生成せず（既存保持）、binary を `_cache/` から再リンク → companion の `id:`（所有権の真実）は不変。Two Media ID Spaces invariant に適合。
- **size 突合・`[MEDIA_CACHE_CORRUPT]` 経路（`:812-819`）は変更なし**: 再展開時も同じ破損検知が走るため、② の修正によって破損キャッシュの復元パスが開くことはない。

### 2.4 可観測性: `[MEDIA_CACHE ...]` ログの扱い（`src/sync/pull/snapshot_pull.ts:347,352,502`）

- `RestoreSnapshotMediaResult` の再展開件数分離（`relinked` フィールド追加）は**本バージョンでは行わない**と決定。同型は公開 façade 由来で Ask First カテゴリ 3 に該当し、かつ「復元された」という事実の報告だけで運用要求は満たされる（Epistemic: 内訳ではなく結果を報告）。
- 既存 `[MEDIA_CACHE captured_at=... restored=N missing=M skipped=K]` 行はそのまま。② の経路で再展開された件数は `restored` に含まれる。

> ※ 将来 `relinked` 分離が必要になった場合、カテゴリ 3 の承認手続きを要する。

### 2.5 スキップ判定 invariant の一元表現（ドキュメント）

「**ミラーの所在判定は物理実体基準、履歴（`media_state`）のみではミラー扱いしない**」を `docs/media-pipeline.md` §5 に一文追記し、`mirrorIndex.has()` → `localPath != null` の 2 箇所（§2.2 (a) / §2.3）が同じ invariant の適用箇所であることを記録する。あわせて `:163` の予算説明に「候補は newest-first で選択される」を明記する。
