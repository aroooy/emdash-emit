## 2. 詳細設計仕様

### 2.1 P0（#2）: `conflicts resolve --accept-local` 後のステータス誤認バグ修正

#### 原因（実測 `src/sync/conflicts.ts:484-504`）

`resolveConflict()` の `--accept-local` 戦略では、quarantine コピー（`conflictContent`）を正本パスへ書き戻した後、`saveSyncState()` で `localHash: calculateHash(conflictContent)` を保存している。一方、`base_snapshots` にはリモート起点の古いベースラインが残るため：

1. `emit status`（`src/sync/status.ts:181-194`）が `syncState.localHash === currentHash` を見て **`🟢 [synced]`** と誤認する。
2. `emit diff`（`src/sync/diff.ts:191-193`）が `isModified = false`（`Status: 🟢 In Sync with base snapshot`）を出力しながら、`:200` の `computeContextDiff` では大量の差分を表示する自己矛盾を起こす。
3. `pushAll`（`src/sync/orchestrator.ts:520-522`）は `syncStatus === 'modified' || 'untracked'` のみ対象とするため、救出した変更がプッシュ対象から漏れる。

#### 修正内容（`src/sync/conflicts.ts:484-504`）

- センチネル文字列（不正な SHA-256 文字列）は DB に書き込まない。
- `const baseSnapshot = options.cache.getBaseSnapshot(id);` と `existingSync` を参照し、以下のように `sync_state` を更新する：
  - `baseSnapshot` が存在する場合（通常の pull 競合）：`localHash: baseSnapshot.hash`、`conflictPending: 0` を保存する。
    - **Rev.4 で追加した実装条件**: `saveSyncState()` は UPSERT のため、`localHash` だけ差し替えて他の列（`remote_rev`, `synced_at`, `delete_pending`, `taxonomy_apply_pending`, `remote_taxonomy_hash` など）を省略・既定値で渡すと既存値が壊れる。v0.1.12 R4 で導入された「`saveSyncState` UPSERT は conflict 列を NULL に落とす」挙動も踏まえ、**`existingSync` の全列をそのまま引き継ぎ、`localHash` と conflict 列のみ差し替える**ことを実装条件として明記する。
    - **Rev.4 で追加したテスト条件**: `baseSnapshot.hash` は Layer A（canonical spelling）のハッシュであり、disk が Layer B（`localMediaRefs: true` 既定）で書かれている通常ワークスペースでは `sync_state.local_hash === disk hash` とならない。よって回帰テストは**必ず `reconstructBaseline()` / `isLocalFileUnmodified()` 経由で `modified` を検証**する（生のハッシュ一致を期待しない）。
    - `conflictContent` が `baseSnapshot` に対して**実質的な差分を持つ場合**、`reconstructBaseline()` の `matchesDisk`（`baseline-reconstruction.ts:68-73`）は `false` となり、自動修復（`retrackLocalHashOnly`）も発火せず、`emit status` は **`🟡 [modified]`**、`emit diff` は **`🟡 Modified`**、`pushAll` もプッシュ対象として正しく拾う（`conflictPending: 0` なので `orchestrator.ts:534` でスキップされない）。
    - なお `conflictContent` が `baseSnapshot` と表記差（`localMediaRefs` 等）しか持たない場合のみ `matchesDisk` が `true` となり `synced` に修復される（実質差分がないため正当な挙動。`tests/baseline_reconstruction.test.ts` H1-② の通り）。
    - **副作用（安全側の仕様）**: `--accept-local` 解決直後に再度別コピーで `--accept-local` を実行すると、`isLocalFileUnmodified()` が `false`（未プッシュ変更あり）を返すため `CanonicalHasUnpushedEditsError` で保護される（上書きするには `--force` が必要）。この旨を `CHANGELOG.md` に明記する。
  - `baseSnapshot` が無く `existingSync` のみ存在する場合：`localHash: existingSync.localHash`（かつ `conflictPending: 0`）を保持する（`existingSync.remoteRev` が新しい場合、push 時は 409 → 3-way merge 経路で保護される）。
  - `baseSnapshot` も `existingSync` も存在しない場合：擬似的な `sync_state` 行を作らず、`saveSyncState()` を呼ばない（`extractBaseArticleName()`（`conflicts.ts:108-119`）が `.conflict.md` / `.deleted.md` サフィックスを除去するため正本パスに書き戻され、ULID を持てば `untracked` として扱われる。`diff.ts:164-172` は `baseSnapshot` 不在時に `ℹ️ No base snapshot found...` を返す仕様そのままを維持）。
- **限定（Rev.4）— `.local-dropped.md` は本修正の対象外**: 退避サフィックスは `.conflict.md` / `.deleted.md` / `.local-dropped.md` の 3 種だが、`extractBaseArticleName()` が扱うのは前者 2 種のみ。`.local-dropped.md` は `pull <id> --force` が **canonical ファイルを unlink かつ DB 追跡レコードも削除**したうえで書く残骸（`docs/sync-engine-and-revisions.md:182`）であり、正本も `sync_state` 行も存在しないため `saveSyncState()` の書き分けそもそもが発生しない。よって本修正の経路外であることを明記する（`.local-dropped.md` の復元経路は別スコープ）。
- **テストで固定する不変条件（Rev.4）— `base_snapshots` は一切触らない**: `--accept-local` は `sync_state.local_hash` と conflict 列のみを更新し、`base_snapshots.hash` / `frontmatter_yaml` を変更しないことを `tests/conflicts.test.ts` で検証する。3-way merge の base（Layer A）が動かないことが本修正の前提。

### 2.2 P0（#3）: `article-search --status draft` での公開記事混入バグ修正

#### 原因（実測 `src/sync/article_search/remote.ts:119-130`）

`mustUseScan = hasTaxonomyFilter || hasDateFilter || !normalizedQuery;` に `options.status` が含まれていないため、`query` + `--status draft` を渡すと FTS 経路（`GET /_emdash/api/search`）へ進み、EmDash 本体の FTS が `status` を無視して公開記事を返す。さらに `RawSearchItem`（`:55-65`）に `status` フィールドが無いため Emit 側での事後フィルタも効かない。

#### 修正内容（`src/sync/article_search/remote.ts:119`）

- `mustUseScan` を以下に修正する：
  ```ts
  const mustUseScan =
    hasTaxonomyFilter || hasDateFilter || Boolean(options.status) || !normalizedQuery;
  ```
- `--status draft` / `--status published` 指定時は必ず `executeScanSearch()` を経由し、`statusesToFetch = options.status ? [options.status] : ['published', 'draft']`（`:456-458` で実装済み）によって `/_emdash/api/content/<collection>?status=<status>` のみを走査する。
- **不変条件**: `--status` 指定時は常に scan パスへルーティングされるため、返却 `hits` の `status` フィールドは必ず埋まる（snapshot enrichment 経由の FTS と異なり欠落しない）。
- **既存文言との整合（Rev.4）**: `CHANGELOG.md:122`（v0.1.46）は設計根拠を「the official FTS endpoint when only a query **and/or status** is supplied」と記述している。本修正は FTS を捨てるのではなく「**FTS が返さないフィールド（taxonomy / 日付 / status）を条件に含めた場合のみ scan へ切り替える**」拡張であるため、`docs/cli-and-mcp-reference.md` の `article-search` 節と `CHANGELOG.md` に「`--status` 指定時は scan パス（scan の件数上限と `[WALK_INCOMPLETE]` セマンティクスが適用される）」を 1 行追記する。

### 2.3 P1（#4）: 引数なし `emit diff` / `emit push` のスマート化（CLI のみ）

> **MCP スコープ外**: `sync_diff` / `sync_push` は AI エージェントの誤操作防止のため明示的な `filePath` / `id` 必須を維持する。

#### 設計原則（二重実装の禁止）

プッシュ・diff 候補の抽出を CLI 側で `iterWorkspaceArticles` を回して再実装しない。Layer 1 の **`getWorkspaceStatus()`**（`src/sync/status.ts`）を使用し、`pushAll`（`orchestrator.ts:520-543`）と同一の判定条件（`syncStatus === 'modified' || 'untracked'` かつ pending フラグなし）で候補を絞る。

- **Rev.4 実装指示 — 候補選別 helper の置き場所は Layer 1 `status.ts`（`orchestrator.ts` ではない）**: pending 列は `ArticleStatusItem` へ **`|| undefined` で格納される**（`status.ts:206-208`）ため、CLI 側に `!i.deletePending && !i.conflictPending && !i.taxonomyApplyPending` を書き写すと `pushAll`（`orchestrator.ts:529-543`）との二重実装となり、将来 pending 列が増えたとき auto-target だけ素通しになる。候補選別を純粋関数として切り出す（例 `selectPushCandidates(status: WorkspaceStatusResult): { toPush: ArticleStatusItem[]; skipped: Array<{ slug; filePath; reason }> }`）。
  - **置き場所の根拠**: `sync/status.ts` は Layer 1、`orchestrator.ts` は Layer 2 であり、**Layer 1 は Layer 2 を import できない**（Axis 1）。したがって helper は **両者から見える Layer 1 の `src/sync/status.ts` に置く**。`pushAll`（Layer 2 → Layer 1 は許可）と CLI（`status.ts` の `getWorkspaceStatus` / `filterStatusItems` は既に import 済み、`layering.test.ts:67-107` の allowlist 変更なし）が同じ関数を使う。
  - **Ask First カテゴリ 3 との整合**: Layer 1 への純粋関数追加であり、`pullBatch` / `pullSingleArticle` / `pushArticle` / `pushAll` のシグネチャ・戻り値形状の変更でも `ALLOWED_LAYER_2_SYMBOLS` 拡張でも Layer 2 sibling edge 追加でもない。

#### A. 引数なし `emit diff`（`src/cli/commands/status.ts:246-261`）

- `-c, --collection <collection>` オプションを追加し（`status` コマンドと揃えて `options.collection || ctx.config.defaultCollection` で解決）、`filePath` と `options.id` が両方未指定のとき：
  1. `getWorkspaceStatus(ctx.root, ctx.cache, collection)` から `syncStatus === 'modified'` の記事を抽出する。
  2. **0 件**: `✨ All tracked articles are in sync with base snapshots. Nothing to diff.` を表示して exit 0（ただし `status.summary.invalid > 0` または `status.summary.untracked > 0` がある場合は、`ℹ️ Note: N untracked / M invalid file(s) exist — run "emit status" for details.` を併記し誤解を防ぐ）。
  3. **1 件以上**: 対象ごとに `inspectArticleDiff({ workspaceRoot: ctx.root, cache: ctx.cache, filePath: item.filePath })` を実行し、連続出力する（複数件時は件数サマリを先頭に表示）。

#### B. 引数なし `emit push`（`src/cli/commands/push.ts:131-135` の `if (!file)` 分岐を置換）

- `-y, --yes` オプションを追加（`Skip confirmation prompt when auto-targeting a single modified article`）。
- **修正（Rev.4）— `--force` は承認系フラグではない**: auto-target で許可するのは `-y, --yes`（確認スキップ）のみ。拒否リストは **`--allow-publish`, `--revive`, `--allow-wipe-taxonomies`, `--allow-unapplied-taxonomies`, `--resolve-taxonomy <strategy>`, `--force`** の 6 件。
  - `--force` を無条件に許可すると Guard G3（published 昇格）／G15（delete-pending 再起動）／G16・G19（タクソノミー上書き）を auto-target で素通しになるため、Rev.3 の「承認系」分類から `--force` を**除外せず拒否側へ確定**させる。
  - **明示パス指定時との非対称を明記**: `emit push posts/draft/x.md --force` は従来どおり受理（既存挙動は無変更）、auto-target で `--force` を渡したときのみ exit 1。
- `file` 未指定かつ `--all` 未指定のとき、`getWorkspaceStatus()` からプッシュ可能候補（`modified` / `untracked` かつ pending フラグなし）を抽出する：
  1. **0 件**: `✨ All valid articles are already in sync. Nothing to push.` を表示して exit 0。
  2. **1 件のみ**: 対象パスを表示したうえで：
     - `options.yes` が true ならそのまま `pushArticle()` を実行。
     - 対話 TTY（`process.stdin.isTTY && process.stdout.isTTY`）なら **`node:readline/promises` ベースの確認プロンプト関数**で `Push "<relPath>"? [y/N] ` を出し、`y` / `yes` のみ実行（それ以外はキャンセルで exit 0）。
       - **Rev.4 実装指定**: Rev.3 の「`Readable` ストリームベース」を差し替え、`src/cli/commands/profile.ts:51-98` の `readSecretLine(prompt, io)` と同一の **`io: { stdin?: NodeJS.ReadStream; stdout?: NodeJS.WriteStream }` 注入シグネチャ**を持つ新関数（例 `readConfirmLine()`、echo マスキング不要なので `setRawMode` なし）を `push.ts` ローカルに置く。テストは `tests/cli.test.ts:504` / `:543` / `:553` が `readSecretLine` に対して行っている `Readable.from()` + fake TTY 差し替えと同型でモック可能。
     - 非 TTY かつ `--yes` なしなら安全のため exit 1 とし、対象パス指定または `--yes` / `--all` を案内。
  3. **2 件以上**: 候補一覧（最大 10 件）を表示し、ファイルパス明示または `emit push --all` を案内して exit 1。
- ※ 従来の引数なし `emit push`（即 exit 1）からの挙動変更として `CHANGELOG.md` に明記する。
