# EmDash Media ID Spaces: `id` vs `storageKey`

EmDash stores media assets in **Cloudflare R2** and describes each asset with a row in the **D1 `media` table**. Every asset therefore has **two distinct 26-character ULIDs**, and they are *not interchangeable*. Emit works with both constantly, so this document is the single authoritative reference for which identifier belongs where.

```text
                    one uploaded asset
                            │
        ┌───────────────────┴────────────────────┐
        │                                        │
   D1 media row                             R2 object
   primary key `id`                        key `storageKey`
   01M67P08DXFTYDPFRTJCC4XMP8              01M67P07X2VPW0MYRRRGMA6T5A.jpg
        │                                        │
        ▼                                        ▼
  GET /_emdash/api/media/{id}          /_emdash/api/media/file/{storageKey}
  (record metadata, authenticated)     (the bytes themselves, public)
```

## 1. The two identifiers

| | **Media record `id`** | **Media `storageKey`** |
| --- | --- | --- |
| What it is | Primary key of the D1 `media` table row | Object key (filename) inside the R2 bucket |
| Shape | Bare 26-char ULID, uppercase | `<ULID>.<ext>` or `<ULID1>.<ULID2>.<ext>`; migrated corpora may use any path such as `uploads/2026/11/sample.png` |
| Used by | `GET /_emdash/api/media/{id}` and every write endpoint (`POST`/`PUT`/`DELETE`) | `/_emdash/api/media/file/{storageKey}` (public file route) and the `src`/`url` of a record |
| Written into Emit as | Frontmatter `featuredImage`, cache column `media_state.media_id`, local filename stem `media/<yyyyMMdd>_<id>-<name>.<ext>` | Markdown body image URLs, companion YAML `storageKey:`, cache column `media_state.storage_key` |
| Generated by | EmDash when the record is created | EmDash when the object is stored (independently of the row) |

**They are generated independently and never match.** For a real asset on the production instance:

```text
media/20261031_01M67P08DXFTYDPFRTJCC4XMP8-Geekworm_Raspberry_Pi_case_04.jpg   ← filename uses record id
media/20261031_01M67P08DXFTYDPFRTJCC4XMP8-Geekworm_Raspberry_Pi_case_04.yaml
  url: https://aroooy.net/_emdash/api/media/file/01M67P07X2VPW0MYRRRGMA6T5A.jpg ← file route uses storageKey
```

Both ULIDs point at the same image, and neither is a typo of the other.

## 2. Where each one must appear

| Location | Correct identifier | Wrong identifier symptom |
| --- | --- | --- |
| Frontmatter `featuredImage:` | record `id` (or `null`) | A `storageKey` here fails preflight Guard **G10** (`INVALID_FEATURED_IMAGE`), or pushes a hero image the admin UI cannot resolve |
| Body `![alt](/_emdash/api/media/file/<...>)` | `storageKey` | A record `id` here returns **HTTP 404** from the public file route |
| Local mirror filename `media/<yyyyMMdd>_<ULID>-<name>.<ext>` | record `id` | — (Emit always names mirrors by record id, so a body URL never equals a local path) |
| Companion YAML `storageKey:` / `url:` | `storageKey` | — |
| `.emit/cache.db` → `media_state.media_id` / `workspace_path` | record `id` | — |
| `.emit/cache.db` → `media_state.storage_key` | `storageKey` | — |

`featuredImage: null` clears the hero image; omitting the field leaves the remote value untouched. A URL that happens to contain a media ULID is accepted with a warning and normalized to the bare ULID, but the canonical form is the bare 26-character record id.


## 3. Why mixing them up looks like data loss

Because the two spaces are unrelated, an identifier aimed at the wrong endpoint produces a response that means the opposite of what you expect:

- `GET /_emdash/api/media/{storageKey}` → **401** without a bearer token, **404** with one. The endpoint keys on the primary key, so it never finds the row no matter how healthy that row is.
- `/_emdash/api/media/file/{id}.<ext>` → **404**. The object exists in R2 under its own storageKey; you simply asked for a different key.

A 404 from either route proves only *that lookup* failed. It is not evidence that the record or the object is missing, and it is never grounds for inserting a new media row — a blind `INSERT` duplicates a record that already exists. Verify by **storageKey** on the server side instead (EmDash admin UI media search, or `wrangler d1 SELECT ... WHERE storage_key = ...`), which is the only key both migrated and freshly uploaded assets are guaranteed to share.

Emit follows this rule in its own wording: unresolved body keys are reported as `⚠️ [UNRESOLVED_MEDIA_ASSET]`, never as "missing records", and Emit mirrors records rather than repairing server data.

## 4. How the two spaces enter a workspace

**Assets uploaded through Emit (`media/drafts/` auto-upload).** Emit sees both halves directly and stores them together, so nothing is ambiguous: `media_state` records `media_id` + `storage_key`, the promoted file is named after `media_id`, its companion YAML carries `storageKey:`, and the body line is rewritten to `/_emdash/api/media/file/<storageKey>`. Re-referencing the same asset from another article reuses the existing record instead of re-uploading.

**Migrated corpora (e.g. WordPress imports).** The migration registers each row in D1 and copies the object into R2, but the imported article bodies already contain baked `/_emdash/api/media/file/<storageKey>` URLs. Emit then reads:

- the **body**, which yields only storageKeys;
- the **featured image**, which migrated rows often leave empty (`featured_image.id: ""`), so nothing usable comes from it;
- the **media list** (`GET /_emdash/api/media?limit=…&cursor=…`), which is paginated newest-first and bounded by `mediaSyncLimit` (default 300). Older migrated assets fall outside that window, so their records are simply never seen locally.

The combination — body keys from the deep past, a newest-first window, and empty featured images — is what makes an old asset look unresolved even when its record and object are both intact. `emit doctor` counts these as "referenced media file(s) missing from disk", which means *no local mirror*, not *broken remote image*: the same URL served by the live site returns HTTP 200 because R2 still holds the object.

## 5. What Emit does when a body key resolves to nothing

Resolution order, confirmed sources only:

1. A record Emit resolved under that ULID (canonical `GET /_emdash/api/media/{id}`, or a media-list entry) → the key is recorded in **`verifiedStorageKeys`**, even if that record reports a different storageKey.
2. Confirmed local mirror metadata (`media/*.yaml`, indexed by its record id and by its storageKey — read from `storageKey:` when present, otherwise recovered from the companion's canonical `url:`, because most migrated companions carry only the URL) → also `verifiedStorageKeys`.
3. Nothing matched → the key stays in **`orphanStorageKeys`** and is surfaced as `[UNRESOLVED_MEDIA_ASSET]`. Emit downloads nothing and invents nothing.

Related invariants:

- **Local mirror names never equal body URLs.** A mirror is named after the record id while its body reference carries a storageKey, so matching the two requires the companion YAML (`storageKey:` / `url:`), not filename guessing.
- **`media/legacy_<storageKey>.<ext>` + `.yaml` residue** was written by an older Emit version that synthesized metadata straight from a file route. Nothing reads it any more, every known-key set excludes it, `--prune` never touches it (it matches no media id), and it must be deleted by hand.
- **`emit doctor --check-media-urls`** probes `HEAD /_emdash/api/media/file/<key>` for references no local source can resolve, and downgrades the ones the origin still serves to an informational note. A served key proves only that the R2 object exists — never that a record is absent. Without the flag, doctor stays offline.
- **`emit doctor --check-media-library`** walks the whole remote library and reports its record count against the number of assets this workspace mirrors, which is what turns "447 references have no local file" into a coverage figure. A library-wide `emit pull-media --all` builds the same index while it downloads, so one pass both mirrors assets and indexes every storageKey.
- **The list endpoint is the only lookup path for a storageKey.** `GET /_emdash/api/media` accepts `cursor`, `limit`, `page`, `mimeType`, `folderId`, `q`, and `includeUsage`; `q` matches filenames only, so a specific body key cannot be searched for. Every item in the response carries its own `storageKey`, which is why a complete walk is what makes an index possible at all.
- **`--strict-media`** re-escalates those informational keys to warnings when you want the strictest reading.
- **An article-targeted pull never reports a storageKey as `failed`.** `emit pull-media --article <id>` collects every ULID a body mentions and looks each one up as a record id, which resolves nothing for a migrated corpus by design. Those ids are counted in `unresolvedIds` (reported as expected), while `failed` counts only references that failed the id lookup *and* every storageKey check. A body key confirmed by a companion `.yaml` is reported as `verified/mirrored`, because the asset it points at already sits under `media/` under its record-id name.

## 6. Practical rules of thumb

1. Reading or writing `featuredImage`, cache columns, or local filenames → **record id**.
2. Writing or resolving any URL under `/_emdash/api/media/file/` → **storageKey**.
3. Looking up an asset you cannot resolve → index the whole library first (`emit pull-media --all`, or `emit doctor --check-media-library` for the counts alone), because the list endpoint is the only one that reports storageKeys. Only after a complete walk should anything be verified server-side (admin UI / wrangler) by **storageKey**, never by guessing a record id.
4. Never register, insert, or "fix" media records from Emit; mirroring is its whole job.
5. A local preview that shows no image for an old article usually means *the asset was never mirrored locally* (media window too small), not that the reference is broken — check `emit doctor --check-media-library` before suspecting the ID spaces.
